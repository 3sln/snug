# P7.9 — D005 re-taken: the native-JS package vs a wasm build behind a JS SDK

Recorded 2026-11-03 by the P7.9 engineer. Decision: **D130** in DEVLOG.

The owner's question (P7.9): what does a real JS user get from the native-JS
package (kin → generated JS) compared with **the Rust build compiled to wasm,
wrapped in a JS SDK with the same public API**? The SDK had to be designed
fairly: batched calls where they help, no needless copies, the boundary
counted rather than hidden.

**Headline.**
- **Raw speed favours wasm.** In Node, Chrome and workerd the wasm SDK is
  1.6–2.5× faster on everything that runs the validator VM or the scanner:
  validate, `schema.decode`, views over large messages, handle and stream
  sources, refusal-heavy input. Compile is 4–10× faster.
- **Codec work is mixed.** In Node, wasm decode takes 0.65–1.40× native's
  time and wasm encode 0.44–1.01×. In Chrome and workerd, encoding a large
  integer array is 1.25–1.54× slower with wasm. The JS value builder and the
  JS host-value walk dominate, and they are JS in either build.
- **Copying into wasm can lose.** Validating a 1 MiB byte-string body costs
  3.4× more with wasm (75 µs against 22 µs), because of the copy into linear
  memory. If the bytes are already in linear memory, wasm is 2.5× faster
  there too.
- **Fine-grained calls are cheap.** A boundary crossing costs about 8 ns
  more than calling the same kin function in JS. Batched navigation measured
  no better than per-step calls.
- **Native JS wins on deployment and memory:**
  - It works under a strict CSP. wasm needs `'wasm-unsafe-eval'`.
  - It needs no init step. workerd refuses to compile wasm at run time, so
    the module has to be shipped as a module binding.
  - Its memory goes back to the GC. Linear memory never shrinks: 100
    released views keep 136 MiB until the instance is reset.
  - It is smaller for most entry points. The wasm runtime module is
    60–83 KB gzip, plus 16 KB of glue, against 57 KB for the native runtime.

**Recommendation: both, with a rule** (below). Native JS stays the default
`snug` package. The wasm SDK is an opt-in for validation-heavy server and
worker workloads that can ship wasm.

## What was built (host/wasm-sdk, host/wasm/src/sdk.rs, host/wasm/src/cc.rs)

The SDK has the same public functions as the native package for every
measured workload. `host/wasm-sdk/test/parity.test.mjs` checks that it gives
identical answers on the same inputs: 6/6 passing. It covers:
- the 216 profile vectors (decode and refusal codes);
- encodings of every accept vector, plus 17 awkward values under 5 option
  sets;
- **byte-identical compiled Programs** for the six study contracts;
- whole validation results: verdict, reason, path and offset;
- views, including the cursor, `path()`, directories and `validateAt`;
- handle and push sources over 1, 7, 1,024 and 65,536-byte chunks, with and
  without a work quantum;
- recovery from instance loss.

Every benchmark row also checks that both builds give identical answers
before it is timed.

**wasm modules.** Both use a plain integer ABI: no wasm-bindgen and no
imports. Both are built by `kin/scripts/wasm-build`, which has new modes
`sdk|sdk-size|sdk-s|cc|cc-size|cc-s` and cargo features `sdk`/`compiler`. The
P1.4/P3.4 default build is unchanged, and `bb vm-test` and `bb scan-test`,
including their wasm arms, pass.
- **Runtime module** (`sdk.rs`, 38 exports): scan, VM validate and validate
  span, the resumable profile (`rscan`) and VM (`vms`) sessions, nav
  primitives, batched navigation (`sdk_nav_path` and the paged
  `sdk_nav_page`), the encode tape interpreter, and Program load with
  vm-verify.
  - Memory comes from std's allocator rather than static buffers, so the
    module starts at 1.06 MiB of linear memory (1 MiB of that is the shadow
    stack) and grows on demand.
  - Wiring only: every accept/refuse decision, head, float width and key
    order is a generated kin function (D003).
- **Compiler module** (`cc.rs`): wraps `host/rust/src/compile.rs`, the Rust
  host's arena loop, the D020 float port and the SOURCE_KEY digest,
  unchanged. It is loaded lazily on the first `compile()`, the way the
  native package loads its compiler chunk.

**Design choices and why.**

| API | SDK design | Why this is the fair design |
| --- | --- | --- |
| `decode` | The wasm profile check (input copied into one reusable, growable buffer), then **the same JS builder over the caller's bytes**. | The bytes are already in JS, and building values is host work (D004). A wasm "tape" for the builder would only replace head parsing, which is cheap: it writes and reads every item an extra time, and object and string creation still happen in JS. Not built; see caveats. |
| `encode` | The JS walk keeps the native admission rules (D113) and bounds. It writes a **tape** into linear memory: ops, plus a byte area for text and byte payloads. **One** wasm call then produces deterministic CBOR with kin's writer primitives. Keys are sorted by kin before any value is written, as in the native walk. | Host values can only be inspected in JS. A per-head wasm call was measured instead (the boundary rows): 22 ns per call against 14 ns for the JS kin function, so a per-item design loses. The tape makes the crossing once per message. |
| `compile` | A separate lazily instantiated module. P and B are copied out to JS, because the public `Program.P/B/serialize/sourceKey` need them. The Program is then loaded into the runtime instance and verified there. | Mirrors the native split. A second module can be dropped to release its memory, which matters (see memory). |
| `validate` / `validateAt` | The input is copied into the reusable buffer. One call passes the 8 limit words as arguments. The out words are read in place, and paths are rendered from the JS copy of the key table. | One crossing per call, and no allocation per call. |
| views | Each view owns a copy in linear memory; the native default (owned) copies too. The check runs on that copy. Every navigation step is one call to a kin nav primitive. Scalars are read in place, with TextDecoder over a subarray of linear memory. **Batched alternatives:** `view.path(...steps)` follows a chain in one call, and `entries()` fetches children 64 per call. | This measures the fine-grained boundary the owner asked about, alongside two batched designs. A first unpaged batch (every child in one call) was 10× slower on an iteration that stopped after 100 of 10,000 children, so it was replaced by paging. |
| sources | Each session's state (rscan or vms scratch, key arena) and its **window** live in linear memory. A handle read is copied in once. The push buffer *is* the session window, compacted in place, so there is no JS buffer at all. | Chunks stream into a reusable buffer, as P7.9 suggests. |
| zero-copy | Measured as rows where the bytes are already in linear memory, standing for a caller that reads a network or BYOB stream straight into an SDK buffer. | Removes the 60 µs/MiB copy. Such a buffer is detached whenever memory grows, so this is an advanced API, not a default. |
| instance loss | Any `WebAssembly.RuntimeError` **or RangeError** escaping a wasm call discards the instance and starts a fresh one from the same module. The failing call throws `InstanceLost`, never a verdict. Programs reload and re-verify lazily. Open views and sessions become unusable. | Stack exhaustion inside wasm surfaces in V8 as a RangeError, not a trap (`trap-probe`, below). It leaves Rust's shadow-stack pointer wherever it was, so the instance cannot be trusted afterwards. |

**API differences forced by wasm.** These are what a user would notice:
- **`await init(source)`, or `initSync(module)`, before the first call.**
  - In browsers the module arrives asynchronously, through `compileStreaming`.
  - workerd allows only an imported `WebAssembly.Module`.
- **Copies instead of aliases.** `bytes()`, `raw()` and `typedView()`
  return copies, because an alias into linear memory is detached by memory
  growth and freed with the view.
- **`borrow` is ignored.**
- **Memory is released late.** A view's linear memory is freed by a
  FinalizationRegistry, or at once by the SDK extra `view.release()`.
- **Error precedence can differ.** When one message holds several encode
  faults, the one reported can differ: the walk visits map members in host
  order, while native visits them in kin order. A single fault gives the
  same code.
- **The encode tape refuses nesting beyond 4,096 levels** with `depth`.
- **Unicode tables are not wired** into the SDK compiler.
- **The public `Writer` was not ported.** It would use the same tape, with
  map-order faults reported at `finish()`.

- **Views are where wasm's memory model bites.** The native package hands a
  dropped view's 1.4 MB back to the GC. In wasm the allocator can reuse the
  space, but the 136 MiB of pages stay mapped until the instance is reset.
- Programs live in wasm and reload lazily after a reset. That costs a
  re-verify, which is 4 ms in Chrome for this Program.

**Trap probe.** Engine stack exhaustion inside wasm is a RangeError, not a
`RuntimeError` (Node 24 / V8 13.6). Five overflows in a row left the scanner
working, because it keeps nothing on the shadow stack. Rust code that takes
the address of a local would be left with a stale `__stack_pointer`. The SDK
therefore resets the instance on any RangeError that escapes a wasm call.

## Recommendation (D130): both, with a rule

**Default: the native-JS package** (`snug`), for every JS host. Keep it the
default because:
- it is synchronous with no init step;
- it is CSP-safe and Workers-safe as a plain bundle;
- its memory returns to the GC;
- it is smallest for codec-only and schema-only users;
- on decode and encode, wasm is not consistently faster (0.44–1.54× across
  rows and runtimes).

**Opt-in: the wasm build behind the SDK** (`snug/wasm` or a sibling
package), when all three hold:
1. **The hot path is the validator VM or the compiler:** validate,
   `schema.decode`, views over large messages, sources, refusal-heavy
   traffic, or compile at run time. There the SDK is 1.6–2.5× (compile
   4–10×) faster in Node, Chrome and workerd.
2. **The host can run wasm:** pages allow `'wasm-unsafe-eval'`; Workers ship
   the `.wasm` as a module binding; the app can `await init()` once.
3. **Memory high water is acceptable:** the process can absorb linear
   memory that never shrinks, or the app calls `reset()` (or
   `view.release()` for views).

**Stay native even then for:**
- validating messages dominated by large byte strings when the bytes are in
  a JS buffer. The copy makes wasm 3.4× slower on a 1 MiB body, unless the
  caller reads straight into the SDK's buffer.
- encoding large integer arrays in browsers or workerd (1.25–1.54× slower);
- code that keeps many views alive.

**Cost of offering both:** about 1,300 lines of SDK JavaScript that restate
host logic (the view, the source drivers and the encode walk), plus two more
wasm builds. Kept identical by `host/wasm-sdk/test/parity.test.mjs`, which
would need to become a gate if the SDK ships. The first release can ship
native only and mark the SDK experimental.

## Caveats

- **The machine was heavily loaded** (load average 100–150). CPU figures
  hold up; Chrome and cold-start wall figures are noisy.
  - Chrome rows are wall time on that machine. workerd CPU carries `ps`'s
    10 ms resolution.
  - The Node cold start is unbundled, so native's import loads 46 modules
    and the SDK's 10.
- **Both builds share one Node isolate.** Earlier work (P7.8) saw ±25% JIT
  history effects on VM JS figures. The interleaving guards against drift,
  not against JIT state.
- **Not built or not measured:**
  - a wasm value-builder tape for decode (argued above);
  - a SharedArrayBuffer-backed shared memory. That needs a threads build and
    cross-origin isolation, and a shared memory would reintroduce the
    mutation-under-check hazard that the native API refuses (review C17).
  - a codec-only wasm module;
  - wasm-opt;
  - Firefox and Safari;
  - Cloudflare production. Local workerd only, never deployed.
- **The public Writer and Unicode compile tables** are not ported to the SDK.
- **The workerd version is 2025-12-17**, from the global bun install. The
  2026-11-02 binary that P7.7 used sat in another project's scratch and was
  not looked for.
- Measured at **93f8718**. P7.1's in-flight profile changes, in kin, the
  scanner, the VM and the JS host, are not included.
