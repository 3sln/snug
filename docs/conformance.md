## Executive summary

snug implements a useful **bounded CDDL subset over a stricter-than-core-deterministic CBOR profile**. It is not currently a validator or decoder for all valid RFC 8949 CBOR, and an accepted schema is not yet a blanket guarantee of RFC-correct matching. The most consequential confirmed matching defects are signed-zero numeric controls and unplugged group sockets. Known tag-content checking is also partial: URI syntax and leap-second validity have counterexamples. The narrower accepted map/array fragment otherwise behaved existentially in the exercised cases.

Inventory: **216 items**, comprising **142 decisions** and 74 semantic/refusal items: **143 conformant**, **43 conformant but incomplete**, **20 deliberate deviation**, **10 non-conformant** (revised by the quotation check above; originally 147/45/18/6). These count reviewed items, including engineering decisions outside the RFCs' remit and overlapping descriptions of the same behaviour; they are not counts of independent defects. Each item receives exactly one classification.

The important conclusions are:

- **D021 does not need a global cut change.** Ruby 0.12.14, Rust 0.10.7 and snug all allow a second group-choice branch after the first branch's cut fails. Killing every map candidate would break valid discriminated alternatives. The supported branch-local reading is conformant; the wording “deliberate choice” overstates its departure from reference behaviour. *(Quotation check: the verified RFC text, §3.5.4 “the entire map fails to match” and Appendix A, is literally global. D021 matches the reference tools but departs from that text, so “deliberate choice” is accurate and D021 is reclassified as a deliberate deviation.)*
  *(Superseded 2026-11-10 by owner decision D301, on the format 2.0 PEG branch: the default cut is the literal RFC 8610 §3.5.4 / Appendix A reading, where a failed cut fails the whole map; D021's branch-local reading is kept as the non-default option `cuts: 'branch'`. Discriminated unions are written as a type choice of maps or with `=>` discriminators; see guide.md, "Discriminated unions under the RFC cut". This audit's classification describes format 1.)*
- **D011/D012 restrict coverage substantially, not merely speed.** Proven flat-map assignment is exact; finite overlapping map counters, some value-disjoint table schemas, coupled group repetitions and non-tail group recursion are refused. A small independent exhaustive interpreter comparison covered **1,840 data/schema combinations** without disagreement or unknown results in the selected supported shapes. That is evidence for the fragment, not a proof of the full compiler or of its oracle's own RFC conformance. *(Quotation check: the oracle's array semantics are existential, whereas RFC 8610 Appendix A specifies greedy PEG matching, so the 1,456 array agreements do not show RFC conformance; see D012/S28.)*
- **Byte validation cannot validate valid non-deterministic CBOR at all.** Indefinite items, non-shortest heads/floats and unsorted maps fail even against `any`, including embedded CBOR, views, handles, push and stream paths. Duplicate keys are different: RFC 8949 treats them as invalid, so their rejection is correct. Encoders producing deterministic bytes does not require all decoders to enforce deterministic input.
- **`f97e00`-only is an additional NaN policy.** Core deterministic §4.2.1 does not by itself impose that unique sign/payload/signaling representation. D122 chooses a §4.2.2-style additional rule. Decimal normalisation, LE typed-array NaN exclusion, top-only tag55799, ndarray rank/extents and hard limits further restrict even otherwise deterministic input.
- **Current default tag coverage is wider than SPEC and parts of cddl-support say.** D180's `tags:'any'` admits COSE/CWT, bigfloat, regexp and MIME tags. Under the default, none of the standard prelude names is inherently empty. `float16-32`, `float32` and `float64` have witnesses under both wire presets.
- **Public JS sequences appeared during the audit and were exercised.** Framing, immediate delivery, empty input, split chunks, limits, EOF and stop/skip worked in 42 targeted public-API runs. They still refuse RFC-valid sequences containing non-deterministic items. No fresh snug Rust/wasm sequence parity claim is made.
- **D230 appeared during the audit.** It directs a future valid-CBOR default and broader CDDL coverage. It is included in the inventory as a pending implementation, not treated as an already completed change. This audit changes no implementation and builds no lenient decoder.

| --- | --- |
| Q1 | [RFC8949 §4.2.1](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1): “Preferred serialization MUST be used.” Preferred shortest representations are further described in §4.1; this is a deterministic-profile encoding rule. |
| Q2 | [RFC8949 §4.2.1](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1): “Indefinite-length items MUST NOT appear.” General §3 still defines valid indefinite strings/containers. |
| Q3 | [RFC8949 §4.2.1](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1): “The keys in every map MUST be sorted in the bytewise lexicographic order of their deterministic encodings.” §4.2.3 describes a different, length-first ordering. |
| Q4 | [RFC8949 §§4.1–4.2.2](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.2): core float encoding uses the “shortest form that preserves the value” (§4.2.1; §4.1 adds that “For NaN values, a shorter encoding is preferred if zero-padding the shorter significand towards the right reconstitutes the original NaN value”). Paraphrase: §4.2.2 discusses additional protocol choices, including NaN representations/signaling/payload semantics and zero/int/float distinctions. It does not make every choice a universal §4.2.1 MUST. |
| Q5 | [RFC8949 §3.4](https://www.rfc-editor.org/rfc/rfc8949.html#section-3.4) (corrected from §9.2): “IANA allocated tag numbers 65535, 4294967295, and 18446744073709551615” … “These tags are not intended to occur in actual CBOR data items; implementations MAY flag such an occurrence as an error.” Refusing them is therefore permitted, not required; “permanently invalid” overstated the text. Simple values 24..31 are “(reserved)” in §3.3 Table 4 (corrected from §9.1, which only lists the registrable ranges 0..19 and 32..255). These are different from unassigned-but-allowed generic values. |
| Q6 | [RFC8610 §§3.2–3.6](https://www.rfc-editor.org/rfc/rfc8610.html#section-3.5), [Appendix A](https://www.rfc-editor.org/rfc/rfc8610.html#appendix-A) (corrected): Appendix A is normative. A PEG “prioritized choice” tests alternatives “in left-to-right order, locking in the first successful match”. “the occurrence indicators ("?", "*", "+") are "greedy" in PEG”, so “"*a a" in CDDL syntax never can match anything”. §3.5.3: array matching “is fully determined by the PEG formalism”. For maps, “a matching member is picked out of the entire map” for each candidate the PEG algorithm tries; in pathological overlapping cases “what is actually picked is indeterminate”, and writers are urged not to write them. An existential (all-derivations) reading therefore matches the RFC for non-pathological maps, but **not for arrays or group choices inside arrays**. The original sentence “No specified implementation requires greedy selection or no-backtracking” was wrong. |
| Q7 | [RFC8610 §3.8.3](https://www.rfc-editor.org/rfc/rfc8610.html#section-3.8.3): “XSD regular expressions are defined in Appendix F of [W3C.REC-xmlschema-2-20041028]”. §3.8.3.1: “"." matches any character but the line-ending characters \r or \n”. (Corrected: “implicitly anchored at both ends” is **not** RFC 8610 or RFC 9485 text. Whole-string matching follows from the XSD semantics, which RFC 9485 §4 makes normative for I-Regexp, and from RFC 9485 §§5.3–5.4, which map to other dialects by enclosing in `^(?:`…`)$` or `\A(?:`…`)\z`.) [RFC9485 §3](https://www.rfc-editor.org/rfc/rfc9485.html#section-3) (corrected from §2) defines the I-Regexp syntax: “essentially an XSD regexp without” character class subtraction, multi-character escapes and Unicode blocks. §4 defines the semantics. I-Regexp is not all XSD syntax, and host regexp behaviour is not normative. |
| Q8 | [RFC8610 §3.5.4](https://www.rfc-editor.org/rfc/rfc8610.html#section-3.5.4) (verified): “once the member key matches the name part of an entry that carries a cut, other potential matches for the key of the member that occur in later entries in the group of the map are no longer allowed. … it "locks in" the pick -- this rule applies, independently of whether the value matches as well, so when it does not, the entire map fails to match.” Appendix A contrasts PEG choice with a cut: PEG choice locks in “(but not disabling alternatives in choices containing this choice, as a cut (Section 3.5.4) would)”. Corrected paraphrase: the literal text is global, so a failed cut also disables enclosing group-choice alternatives. The original paraphrase (“Choice alternatives can still supply another match”) is the reading that D021 deliberately adopts, in agreement with the reference tools. It is not what the text says. §a runs both tools on this distinction. |
| Q9 | [RFC8742 §2](https://www.rfc-editor.org/rfc/rfc8742.html#section-2): paraphrase: a sequence consists of concatenated complete CBOR items, with no enclosing array or inter-item delimiters; zero items is allowed. A truncated tail is not a complete item. This does not impose a deterministic-input restriction. |
| Q10 | [RFC8610 §3.9](https://www.rfc-editor.org/rfc/rfc8610.html#section-3.9): an unplugged socket is an “empty type choice” / “empty group choice” (quoted phrases). Paraphrase: no alternatives is not the empty group, which has one empty derivation. |
| Q11 | [RFC8610 §3.8](https://www.rfc-editor.org/rfc/rfc8610.html#section-3.8): paraphrase: `.lt/.le/.gt/.ge/.eq/.ne` impose their comparison/exclusion constraints (§3.8.6); `.size` counts string bytes and unsigned magnitude sizes (§3.8.1), `.bits` enumerates permitted positions (§3.8.2), `.and/.within` impose both matching predicates (§3.8.5). Corrected: `.default` is not merely an annotation. §3.8.6 says “A variant of the ".ne" control is the ".default" control … and the implied .ne control is there to prevent this value from being sent over the wire.” Erratum 9229 (status Reported, not verified, 2026-10-16) proposes the annotation-only reading. |
| Q12 | [RFC9165 §§2–4](https://www.rfc-editor.org/rfc/rfc9165.html#section-2): paraphrase: `.plus`, `.cat`, `.det`, `.abnf`, `.abnfb`, `.feature` add semantics beyond the base controls. Feature annotation does not by itself require snug to reject a matching target or invent feature-negotiation policy. `.pcre` is an illustrative/proposed alternate dialect in RFC8610 §3.8.3.2 (“a proposal for a ".pcre" control is defined in [CDDL-Freezer]”), not a requirement to ship a host PCRE engine. |
| Q13 | [RFC9682](https://www.rfc-editor.org/rfc/rfc9682.html) (corrected): grammar updates to RFC8610 Appendix B only. §2.1 adds the `\uXXXX`, surrogate-pair and `\u{hex}` escapes and tightens SCHAR/BCHAR/PCHAR. §3.1 allows a file with zero rules (`cddl = S *(rule S)`). §3.2 allows `#6.<type>` **and `#7.<type>`** head numbers; for `#7`, 24..31 “stands for the "additional information"” (e.g., `#7.25` is float16). It does **not** change the prelude, sockets or matching semantics. Appendix A replaces the collected ABNF. |
| Q14 | [RFC8746 §§2–3](https://www.rfc-editor.org/rfc/rfc8746.html#section-2): paraphrase: typed-array tags describe element type/endian/width in byte-string payloads; multidimensional tags40 and1040 use row-major and column-major ordering, and their dimensions are “unsigned integers distinct from zero” (§3.1.1; tag 1040 is “The same as tag 40” except for order). The scalar-CBOR shortest-float requirement does not re-encode IEEE elements stored inside byte strings. |
| Q15 | [RFC8949 §§5.3,5.6,6](https://www.rfc-editor.org/rfc/rfc8949.html#section-5.3): paraphrase: distinguish well-formed, valid and application-expected input; duplicate map keys and malformed UTF-8 are invalid. A generic decoder's handling of opaque tags is different from a promise to validate all known tag content. Host representations need not preserve every CBOR distinction, but this must be disclosed. |

## (a) D021: what a cut kills

The critical distinction is **another member in the same branch** versus **another alternative of the group**. A cut is not a process-wide flag attached to a CBOR map object.

Executed examples (`E1/E2`; `r` is always first and explicitly selected by snug):

| Schema / synthetic data | snug | Ruby0.12.14 | Rust0.10.7 |
| --- | --- | --- | --- |
| `r = {kind:"a", x:uint // kind:"b", y:tstr}` with `{kind:"b",y:"z"}` | valid | rc0 | rc0 |
| Same choice nested as `r = {(kind:"a", x:uint // kind:"b", y:tstr)}` | valid | rc0 | rc0 |
| `r = {(a:uint // a:tstr), b:bool}` with `{a:"s",b:true}` | valid | rc0 | rc0 |
| `r = {(a:uint // * tstr => any)}` with `{a:"s"}` | valid | rc0 | rc0 |
| `r = {? a:uint, * tstr => any}` with `{a:"bad"}` | invalid | rc1 | rc1 |
| Explicit cut `r = {? "a" ^ => uint, * tstr => any}` with `{a:"s"}` | invalid | rc1 | rc1 |
| Cut-free `r = {? "a" => uint, * tstr => any}` with `{a:"bad"}` | valid | rc1 | rc1 |

The last row exposes **reference implementation limitations**, not a reason to insert a cut into `=>`. Its first entry may match zero times and the absorbing entry can consume the pair. Both reference tools commit too early on this cut-free example. Their behaviour is not uniform evidence for a “global-map-fails” rule: they explicitly accept the preceding group alternatives.

D021 is classified **conformant**, with supporting operational evidence for the contextual reading of §3.5.4. *(Quotation check: reclassified **deliberate deviation**. The verified §3.5.4 text ends “so when it does not, the entire map fails to match”, and Appendix A says a cut disables “alternatives in choices containing this choice”. The branch-local reading is the documented D021 choice shared by both reference tools. The last table row's snug verdict is directly confirmed by §3.5.4's own example: `{ "optional-key": "nonsense" }` “does match this specification”.)* There is no demonstrated need to turn it into a global poison flag. A true cut must still stop fallback to a later wildcard in its branch. Unsupported cut placements are a separate coverage issue: `{* tstr ^ => uint}`, wildcard-before-literal cuts and byte/float/bignum colon keys are valid expressive forms that snug does not support. `=>` is a rewrite only when losing cut semantics is acceptable; it is not a generally equivalent rewrite of `:`.

## (b) D011/D012: exactness and coverage

For an accepted **flat cut-free map** alternative, every constrained entry (positive minimum or finite maximum) has a key domain disjoint from other constrained entries. An overlapping lower-priority entry must be absorbing. If a pair can satisfy the constrained entry, assigning it there cannot prevent any other constrained minimum from being met; the absorber has no lower/upper quota to lose. If its value fails, the pair may go to an accepting absorber instead. Hence greedy assignment is equivalent to existence of a total assignment **under that proof condition**. This is not a proof for arbitrary map groups; factorisation, expansion and cuts each need their additional invariants.

The local independent interpreter experiment enumerated all64 maps over keys a/b/c with absent/uint/tstr/bool values for six supported shapes, including cut-free fallback, optional factor groups and repeated choices. Four array shapes covered every array of length0..5 over three values (364 each). The result was **1,840 equal Boolean verdicts, no unknowns**. No theorem about every accepted compiler output follows from a finite experiment, and the local oracle shares the project's unplugged-socket assumption. Do not use D022/D116 as an independent justification of that assumption.

Concrete valid-but-refused coverage examples:

```cddl
; A total assignment exists for {a:1,b:2}; compiler refuses map_overlap.
r = { 1*2 tstr => uint, 1*2 tstr => uint }

; Same key class, disjoint value classes; {a:1,b:"b"} is assignable.
; Ruby accepts it; snug still refuses map_overlap.
r = { tstr => uint, tstr => tstr }

; Counts may be 0,2,4, not a single interval; compiler map_group_occurrence.
; Both {} and {a:1,b:2} are valid, and Ruby accepts both.
r = { 0*2 (2*2 tstr => uint) }

; Repeated group carries coupled literal and wildcard occurrences.
; Valid schema, refused map_group_occurrence.
r = { 2*2 (? a: uint, * int => uint) }

; A finite derivation [1,"x"] or [1,2,"x","x"] exists.
; Rust accepts; snug refuses group_recursion.
r = [g]
g = (uint, ? g, tstr)

; Valid bounded repetition; default unrolling cap is insufficient.
r = [? uint, 2*500 uint, tstr]
```

In contrast, `[? uint, 2*3 uint, tstr]` accepts `[1,2,"x"]` and `[1,2,3,4,"x"]` in snug. Ruby and Rust reject the shorter array. *(Corrected by the quotation check: under RFC 8610 Appendix A's greedy PEG semantics `? uint` consumes `1` and `2*3 uint` then fails, so `[1,2,"x"]` is **not** valid. Ruby and Rust are right, and snug's acceptance is the S28 defect.)* A million-element *unambiguous* counter schema can compile without a million positions. Thus refusal is driven by overlap/representation limits, not just large occurrence syntax.

### Expected prevalence in published CDDL

## (c) Valid CBOR, deterministic CBOR, and NaNs

Core deterministic encoding is a protocol restriction on encoding choices. General CBOR defines definite **and indefinite** strings/containers, multiple legal argument/float widths and arbitrary map member order. A CBOR decoder can be intentionally restricted, but that scope must be stated independently of its CDDL predicate accuracy.

**The implementation tested cannot validate valid non-deterministic CBOR on any exercised public path, even when the rule is `any`.** It has no bypass option. `compile(...,{profile:'full'})` affects CDDL coverage, not wire acceptance. D230 directs a change, but does not supply one.

| Bytes | General CBOR / deterministic issue | Every exercised current path |
| --- | --- | --- |
| `9f01ff` | Valid indefinite array `[1]`; §4.2.1 disallows indefinite items | `indefinite` / `cbor/indefinite` |
| `1801` | Valid nonpreferred unsigned1 | `non_shortest` |
| `fa3fc00000` | Valid float32 1.5, representable as float16 | `non_shortest` |
| `a2616200616100` | Valid unsorted `{b:0,a:0}` | `key_order` |
| `a2616100616101` | Well-formed **invalid** duplicate-key map | `duplicate_key` (correct refusal) |

The paths actually run were codec decode, schema validate/decode, profile/schema views, profile/schema handles, known/unknown push, profile/schema unknown streams and detached validateAt. Sequence APIs were checked separately. Direct low-level session steps were exercised through those drivers, not exhaustively for every possible scheduling/window split; encode naturally emits only preferred forms. Embedded `.cbor` and tag24 checks inherit the restriction. A valid outer deterministic byte string containing `1801` can fail `.cbor uint`; a plain `bstr` need not examine its payload.

NaN policy requires separate reasoning:

- §4.2.1 requires shortest widths that preserve the chosen value semantics. It does not independently erase all NaN signs, payloads and signaling distinctions.
- §4.2.2 asks protocols to settle additional deterministic choices. Selecting a single quiet NaN `f97e00` when those distinctions are irrelevant is a legitimate **additional policy**. Describing it as required by §4.2.1 alone is too strong. “CDE” should identify a specific external profile/version; it is not another name for every optional choice in RFC8949 §4.2.2.
- A NaN whose meaningful payload cannot be retained in a narrower width is not automatically “non-shortest” merely because a different, payload-free NaN fits binary16. A protocol that discards payloads can choose differently, as D122 does.
- Tests accept `f97e00`, reject `f9fe00`, `f97e01`, `f97c01` and `fa7fc00001` with `float`, and reject wider canonical quiet NaN `fa7fc00000` with `non_shortest`. These are profile verdicts, not proof those encodings are malformed or universally invalid CBOR.
- Infinities and signed zeros can use binary16; finite floats use shortest exact width. Integral floats such as `f93c00` remain legal §4.2.1 values. A JS number round trip can turn1.0 into integer1; `Writer.float(1)` preserves a float encoding.

D181's preferred minimal bignum representation is justified by §3.4.3/§4.1; its128-byte limit is separate. Tag4's negative-only exponent, nonzero/non-factor10 mantissa are **not** required by §4.2.1: `4([1,1])`, `4([-1,0])` and other nonnormalised decimal representations have RFC meanings. Top-only55799 and recursively deterministic tag24 contents are also local restrictions. A general decoder option is a pending owner direction/option, not work performed by this audit.

Unknown custom names produce `unknown_control`; registered controls are target AND predicate. `.chars/.unique/.samelen` are library extensions, not RFC controls. `.unique` means distinct **encodings**, not every conceivable application-equivalence relation. The fixed control maximum and declared host costs limit support, not the RFC's language; arbitrary host callback CPU cannot be proven bounded by this audit.

**Separate correctness defects in accepted controls:** `float .ne 0.0` and `.ne -0.0` accept both zeros; `float .lt 0.0` and `float .gt -0.0` accept both zeros. `float .ne 1.5` excludes the literal correctly but also rejects NaN, unlike the expected negated-equality semantics and Ruby. Bounded `(0.0..1.0) .ne 0.0` rejects both zeros, so source spelling changes the outcome. Treat interval/zero/NaN lowering together. Other exercised finite controls worked where homogeneous literals were accepted. Mixed `float .lt 1` is refused, whereas `float .lt 1.0` compiles; current “exact conversion on either side for small values” documentation is too broad. Integer1 and float1.0 are distinct CBOR kinds; this report does **not** infer a mixed-kind `.eq` bug merely because a host compares their numeric values equally.

## (e) XSD regexps versus I-Regexp

RFC8610 §3.8.3 points at XSD AppendixF. RFC9485 defines an interoperable subset, which snug selected to obtain a portable bounded automaton. That is a sensible engineering choice with a stated reason, but it is not full XSD coverage.

Concrete valid XSD features refused by snug include `\d`, `\w`, `\s`, XML name shorthands `\i`/`\c`, Unicode block escapes such as `\p{IsBasicLatin}`, and character-class subtraction such as `[a-z-[aeiou]]`. The first three and subtraction were actually compiled and compared to Ruby; the names `\i`/`\c` are listed from XSD language knowledge, not claimed as separately executed probes. General_Category escapes (`\p{L}`, `\P{Nd}`) work with the optional Unicode module; they are not globally absent any more. Lookarounds/backreferences and JS `\x` escapes are not baseline I-Regexp syntax and need not be silently accepted.

Anchoring is correct in the exercised common subset: `[0-9]+` accepts`123`, rejects`x123`, `123x` and a trailing newline. Dot rejects both LF and CR and accepts one astral code point. XSD/I-Regexp do not assign PCRE assertion meanings to literal `^` and `$`: snug's `"^x$"` matches the three-character string`^x$`, not`x`. Both reference tools did the opposite; Ruby's dot also accepted CR. These are useful reasons not to copy a host regexp dialect or reference result without applying the RFC grammar.

The supported option should be named precisely, particularly after D230 requests a portable XSD option. This audit chose no new default and implemented neither engine. A probe of `.iregexp` produced `unknown_control`; no claim is made here that every proposed dialect/control spelling is mandatory merely because it names the RFC9485 format.

## (g) RFC8742 sequences: what exists now

Architecture §18 and D210–D219 are no longer merely empty API designs in the JS working tree: `public-sources.mjs` exports `readSequence`/`sequenceReader`, backed by `sequence.mjs` and generated session sequence mode. The audit used those **public** functions. At the start of the audit those exports were absent; their arrival and later probe results are recorded explicitly.

Observed in42 cases:

- Empty stream yields no messages and no error; concatenated scalar/container messages get correct0-based index, absolute message offset and length.
- Whole,1-byte and2-byte chunking give equal bytes and verdicts. A one-chunk message is borrowed; spanning messages are assembled; `copy:'always'` owns the result.
- `sequenceReader().feed(01)` returns the first message immediately, without waiting for EOF or a byte of the next message. An enclosing array is not invented.
- EOF after `01 19` delivers message0, then `truncated` at message1 offset1. Invalid CBOR/profile items stop; earlier messages remain delivered.
- Schema stop on `01 6161 02` yields index0 then a schema/type fault at index1. Skip yields indices0 and2, reports one skipped item, and continues only because framing is intact.
- `maxItems:1` resets for each of three scalar roots. A message over maxMessageBytes fails `too_large`; no total-sequence cap is imposed. Self-described-CBOR tag55799 is accepted at each message root.

This satisfies the exercised framing/EOF behaviours, but only for the admitted profile. RFC8742 also permits items encoded with indefinite forms/nonpreferred arguments; these are still refused. An independently usable general sequence API therefore depends on the D230 input-policy work. The schema `.cborseq` feature is separate: it operates inside bstr and uses a virtual array to impose positions/occurrences.

Neither the full `bb sequence-test` nor fresh Rust/wasm parity was run. Concurrent Rust sequence files appearing in status are not evidence this auditor built them. D219's deferred wasm SDK reader remains incomplete. Diagnostic precedence, offsets for embedded faults, every split, very long streams, quantum fairness and cancellation were not exhaustively verified here. Those limitations do not invalidate the42 observed cases.

## (h) RFC8746 typed arrays; tag40 and1040

D180 fixed the major tag-whitelist coverage issue. Under tags:any, assigned typed-array tags64–87 (except reserved76) are admitted with byte-string/whole-element-length checks. Earlier Bindle-specific LE tags still materialise as native arrays/Float16Bytes; other typed tags remain `Tagged`. A generic tagged representation is allowed; it need not materialise the BE forms to claim their bytes can be read. A uint8 typed tag64 is distinct from a plain untagged CBOR byte string.

Actual checks: big-endian uint16 with two payload bytes passes; odd payload length fails. Tag64 over text fails; tag64 over one byte passes. **LE float16 NaN** `d85442007e` fails typed_array, while **BE float16 NaN** `d850427e00` passes. Scalar shortest-float/NaN policies do not apply inside opaque IEEE byte payloads. The discrepancy is an inherited Bindle/host-value restriction, not an RFC8746 requirement.

Row-major tag40 accepts the tested2×2 shape/data array, but rejects rankzero with one scalar and a zero extent with empty data; rank>8 is additionally excluded by the documented cap. RFC8746 §3.1.1 does require the dimensions to be “unsigned integers distinct from zero”, so refusing a zero extent is correct (corrected by the quotation check). Only the rank bounds (rank zero, rank > 8) are local. They should be treated as an optional restricted NDArray profile.

Column-major tag1040 passes as an opaque tag, and `1040(null)` also passes. Therefore snug can transport the generic tag but does **not** validate its multidimensional structure or expose the same NDArray interpretation as tag40. Both external validators accepted the invalid-null example too; they are not a tag1040 validity oracle. This is **incomplete semantic-tag support**, rather than an assertion that generic opaque-tag decoders must know the entire registry. If the API advertises known-tag validity (as D230 directs), add tag1040 structural validation and distinguish that contract from opaque transport.

## (i) RFC9682 grammar, prelude and sockets

*(Quotation check: RFC 9682 changes only the grammar: string escapes, empty rule files and `#6`/`#7` head numbers. It does not change the prelude or sockets. The socket rule below is RFC 8610 §3.9.)* The exercised updated grammar works: `"\u0041"`, `"\u{1f600}"`, paired surrogate escapes, tabs, byte-literal whitespace/comments and named/nonliteral tag-number constraints. Lone surrogate escape is refused as syntax rather than becoming invalid UTF-8. `#6.<16..18>(uint)` admits16/17/18; `#6.<16 / 18>(uint)` and a named equivalent exclude17. The Rust reference accepts17 in the union test, so the reference is not a reliable tag-constraint oracle for every form. `#6.<uint>(any)` and a64-bit tag constraint were also exercised. No claim is made that every updated grammar production/edge case has been exhaustively tested.

The definite socket defect is simple:

```cddl
r = [$$x]                    ; with no plugs: snug accepts []
r = { a: int, $$nothing }    ; with no plugs: snug accepts {a:1}
```

Ruby and Rust refuse both. An **empty choice has no derivations**, whereas an **empty group has one empty derivation**. Optional/repeated-zero occurrence can explicitly permit absence; it must not be added implicitly to an unfilled required socket. An explicitly plugged socket using `//=` behaves correctly in the tested array example. Current architecture/cddl-support and the local oracle encode the erroneous empty-group rule; change that corpus expectation along with the implementation. A reference-crate issue number in architecture is not a substitute for §3.9's semantics.

D031 also intentionally allows prelude-name replacement. The test `r=uint; uint=tstr` is accepted/shadowed by snug and Rust, while Ruby reports duplicate prelude rule definition. The report conservatively records this as a **documented portability deviation/interpretation**, not a claim that every tool permits redefining standard names or a reason to change the actual standard prelude. Duplicate `=` within user text is still refused.

The prelude text itself tracks the standard integer/float/tag definitions used by the probes. Undefined simple23 is a real valid data value under the default; lack of values under a wire profile is not an undefined name. High simple numbers are a separate grammar/coverage gap: `#7.32` is refused at compile time although simple32 is an allowed generic CBOR value.

## (j) Invalid tags, simple values, float widths, and validity claims

RFC8949 §3.4's three all-ones tag numbers (which “implementations MAY flag … as an error”) are consistently rejected at all exercised public paths, including any-tag mode.64-bit tag numbers do not accidentally take the low32-bit tag's special-content rule in the tests. A nonshortest tag head is still outside the deterministic profile. Unknown but assignable tag numbers may remain opaque; that is different from treating a tag number that is “not intended to occur in actual CBOR data items” as unknown.

Major7 has three separate categories: assigned simple values20–23, unassigned permitted values0–19/32–255, and reserved values24–31. Snug admits false/true/null and default undefined, refuses reserved forms, and also refuses unassigned-but-valid simple values. The latter is support incompleteness. Compiling `#7.24` to an uninhabited valid-data predicate is not the same as accepting illegal CBOR bytes; `f818` is refused at runtime. *(Quotation check: under RFC 9682 §3.2, `#7.24` stands for additional information 24, which means simple values 32..255. It is not inherently uninhabited; it is empty in snug only because S06 refuses simple values 32..255. `#7.<type>` is also a syntax error in snug. These are coverage gaps alongside S35/S36.)* Refusal codes (`simple`, `non_shortest`, `indefinite`, etc.) need not exactly mirror the RFC's well-formed/valid taxonomy, provided the application does not mistake every local profile fault for malformed CBOR.

Float widths select actual encoded width; numeric range comparisons use widened values. Signed zeros compare numerically equal for the tested literal/range semantics. The accepted-control defects in §d are therefore inconsistent with snug's own literal equality, not a request to change `float32` into “any value representable as float32”. *(Corrected 2026-11-11, D328: RFC 8610 §3.3 does make `float32` "any value representable as float32" — the widths are sets of values at the data model level, not serialization constraints — and snug now implements that; see the note above.)* NaN falls outside ordered ranges, but exclusion by `.ne` must not be silently implemented as “ordered and outside a singleton” when the target itself admits NaN.

Known tag content remains a qualification on the claim of validity:

- Tag32's `http://[x` is not a syntactically valid RFC3986 URI; snug and both references accept it. D121 explicitly defers full parsing, so this is classified deliberate underchecking with a stated reason.
- Tag0 accepts `2024-01-01T00:00:60Z`. Second60 is not generally allowed at an arbitrary minute/date: RFC3339 §5.7 restricts leap seconds. Ruby rejects this case; Rust accepts. The broad known-date-validity claim is non-conformant here.
- Opaque tag5/1040 transport does not establish semantic validity of their content. The prelude `bigfloat` still imposes its array shape when actually selected; `any` does not imply full IANA-registry validation.
- A deterministic map with integer1 and float1.0 keys passes schema/view but codec materialisation fails`unsupported` because JS Map merges those keys. It is a representation limitation, not a CDDL mismatch. Lossless general decode needs an explicit map/numeric representation policy.

Documentation that needs reconciliation after an implementation decision: SPEC's obsolete default tag set and older no-Unicode statements; cddl-support's initial undefined/uninhabited and later bigfloat/MIME refusal statements; claims that float literals always compare wire bytes and `0.0` cannot match−0; program §8.4's original per-item `.cborseq` model versus D040's virtual array; program/API paragraphs calling the loader1.0 despite1.1 support; earlier architecture “ANY gives ANY” and source/memory statements superseded by D043/D094/D160. These are S74; changing unrelated docs was outside this task, so they are reported rather than edited.
