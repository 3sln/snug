# Independent review: architecture §17

2026-10-29 · Codex · design review, not an implementation sign-off.

**Verdict: keep the no-I/O resumable core, but revise §17 before building the
general VM or publishing the source API.** A window is a useful transport
boundary, not a complete execution or ownership contract. The current design
has blockers in stream error precedence, suspended scratch ownership and
blob snapshot integrity. Its small-memory claim is false for nested maps;
its key cap changes the accepted language. These are not reasons to abandon
D027. They are reasons to make its contracts explicit and start smaller.

Read: AGENTS.md, SPEC.md, DEVLOG.md (including D016/D017/D026/D027), all of
docs/architecture.md, docs/program.md §§12–14 and the relevant leaf, map,
embedded and witness definitions, docs/scanner.md, bench/SCAN.md, and the
read-only 3sln.me `docs/spec/cbor.md`. Also inspected the existing kin
scanner/helpers, JS builder and local cbor.mjs baseline. §16 is context here;
this review addresses its interaction with sources rather than reviewing
its design independently. No network was used.

## Findings

### 1. [blocker] Unknown-length streams cannot inherit the scanner's check order merely by suspending

**Where:** §§17.1–17.3; scanner “Top level” and “One item”.

The scanner knows the complete document end before checking anything. A
stream does not. This changes more than the moment `truncated` is raised:

* `82 ff` with `top: any` is `truncated`: the two-element array's minimum
  remaining-length check precedes interpreting `ff`. If one more byte arrives,
  `82 ff 00` is `indefinite`. Returning `indefinite` on the first chunk is wrong.
* `63 ff` is `truncated`, whereas `63 ff 00 00` is `text`. Incremental UTF-8
  failure cannot necessarily become an immediate final refusal.
* With `maxEntries: 1`, `82 ff` still gives `truncated`, not
  `too_many_entries`.
* An input starting with `a0 ff` but eventually exceeding `maxBytes` gives
  `too_large`, before `trailing`. A stream cannot know that from its prefix.

These baseline results were exercised locally. The same problem applies to
tag payload lengths and to the outer byte string enclosing `.cbor`.

**Fix:** distinguish **known exact document length** from **unknown length**
in the source protocol. A known-length stream may use that end for the
existing checks without possessing all its bytes. For an unknown-length
stream, explicitly choose between preserving codes with deferred refusals
and bounded draining, or documenting a different refusal precedence. The
latter needs a deliberate change to R7 and the cross-source promise. Do not
let each adapter choose.

Preserving precedence need not require retaining the entire message: a
driver can retain pending errors and collect enough length evidence, or drain
to EOF/the byte cap after an error. But it requires a specified algorithm,
error priority, charging and terminal drain state. It also trades prompt
failure for waiting on a potentially stalled sender. Transport deadlines and
abort remain necessary. Never interpret an empty chunk as EOF.

### 2. [major] `NEED` needs a complete progress, EOF and ownership protocol

**Where:** §§17.1–17.2; the push `feed` API.

“Heads are never split” can only mean the VM receives a coalesced head. The
source is allowed to deliver a nine-byte head one byte at a time. Asking
unconditionally for nine bytes can stall on the valid one-byte document
`a0` while a sender keeps the connection open. Reading the first byte tells
the VM whether the head actually needs 1, 2, 3, 5 or 9 bytes; reserved AI can
be rejected without reading argument bytes.

`feed(chunk) -> NEED/DONE/ERROR` also does not say which bytes were consumed,
whether the caller must keep a tail alive, or how the caller signals that no
more bytes exist. Finishing the root is not `DONE` for an unframed stream:
later bytes can make it `trailing` or `too_large`.

**Fix:** specify a session with start/resume/finish/abort and distinct
statuses for input needed, scheduling yield, root complete but awaiting
document end, success and failure. Define exact coverage required by each
request, partial fulfilment, consumed position, maximum window size, window
lifetime and invalid-fulfilment behavior. Carry at most eight prefix bytes
when coalescing a split head. Stream validation must never request already
discarded source bytes; internal key replay must be distinguishable from a
source request. Repeated resumes without new evidence must neither charge
again nor spin. External framing may supply document end before transport EOF.

### 3. [major] The key limit is a compatibility change, even if today's accept vectors pass

**Where:** §§17.2, 17.6; D026's conformance floor; SPEC §3.

cbor.mjs has no independent map-key length cap. I encoded and decoded maps
with one ASCII key of 1,025 bytes and 65,537 bytes using the local baseline;
both were accepted under default limits. Their total encodings are 1,030
and 65,544 bytes, well below 1,500,000. The proposed default rejects the
first; even its hard maximum rejects the second.

I also decoded the imported vectors with the baseline (`top: any`) and
traversed accepted maps. The 74 profile accepts have maximum UTF-8 key length
9 bytes; the 315 Bindle-valid accepts in the 930-case cborg file have maximum
615 bytes. Thus **no currently accepted fixture would expose this change**.
This is not evidence of profile equivalence, nor a certification of refusal
code precedence under an implementation that does not exist yet.

**Fix:** withdraw the new mandatory cap from the compatibility path, or
explicitly ask for a profile change with new vectors and a decision. Applying
it to all sources preserves agreement between those sources, but does not
preserve cbor.mjs semantics. If retained as an optional resource restriction,
define payload versus encoded length, its reason code, precedence against
UTF-8/truncation/order errors, and the effective compiled/per-call setting.
Do not invent a cbor.mjs profile code for it. A lower default still changes
default compatibility; a hard 64 KiB ceiling cannot offer the original floor.

### 4. [major] Previous-key storage is per active map, not per validation

**Where:** §17.2's `2 × keyLimit + 136` bound.

Consider a map whose first key is long, whose first value is another map,
and which has another pair after that value. While reading the inner map,
the outer map must retain its key to compare with its next sibling key.
Repeat to the depth limit. A single global previous/current pair is
insufficient. Merely calling those bytes “frame stack” hides the missing
allocation; program.md §12's frames have no such storage.

For bounded keys, straightforward storage is O(active-map-depth × keyLimit),
plus current-key and predicate state. At depth 32, retaining two 64 KiB
buffers per map is about 4 MiB; at depth 256 it is about 32 MiB, before VM
state. Defaults and hard maxima need separate accounting. Actual active
encoded key spans are disjoint, so a shared arena can also be bounded by the
document byte cap rather than reserving every depth's worst case.

**Fix:** publish a scratch formula covering retained keys at every physical
depth, including embedded documents. Include it in scratch sizing, total
memory caps and concurrent-session limits. Buffer/immutable-handle drivers
may retain offsets instead and reread; forward-only drivers cannot rely on
that. Source-specific scratch need not change Program semantics.

### 5. [note] Exact key order has a worst-case linear-state lower bound, but two complete key copies are not essential

**Where:** §17.2 and alternatives to its key cap.

For unrestricted equal-length text keys with arbitrarily long common
prefixes, a forward-only deterministic checker must distinguish all possible
previous keys to answer “equal, smaller, larger” for the next key. States for
two different previous keys cannot be merged: presenting the smaller one
next requires different outcomes. That requires Ω(key length) bits in the
worst case. A fixed rolling hash cannot establish exact equality and does
not establish lexicographic order; adding a cryptographic hash changes
exactness into a collision assumption. Prefix compression helps some inputs,
not the worst case. Encoded heads often settle order for different lengths,
but equal lengths remain adversarial.

One previous-key buffer per active map is sufficient for **order alone**:
compare each incoming byte to its old position, then overwrite that position
with the current byte. Retain the comparison result but report it only after
the current key's own profile checks, as the scanner requires. The resulting
buffer now holds the current key. Manage lengths and growth safely.

**Fix:** present the real choices: retain keys, reread an immutable random
access source, spool externally, or explicitly restrict accepted keys. The
same buffer can support later literal search/replay, but two whole copies
are not an information-theoretic requirement. Account for every replay scan.

### 6. [major] A carried literal position handles `LIT`, not general `LITSET` binary search

**Where:** §17.2; program.md §§4.2, 8.3, 14.

A long text or byte-string `LIT` is easy: keep an independent position and
mismatch flag for each admitted literal leaf while bytes arrive; pool bytes
remain resident. Continue the profile scan even after a mismatch.

A `LITSET` uses binary search. Suppose same-length literals share a 10 KiB
prefix. Comparing the incoming item with the first pivot can decide its
branch only at the last byte. The next pivot comparison starts at byte zero,
which is gone on a stream. “Literal-compare position” alone cannot execute
the specified algorithm. This also affects literal-key search, though
retaining the complete current key makes that case straightforward.

Long keys queried against key typesets additionally need full UTF-8,
regexp and literal/control evaluation. Either replay the retained key before
reading its value or construct all key queries before its content and feed
them concurrently. Finding a literal key id is not the key-typeset verdict.

**Fix:** specify retained replay, a streaming prefix/trie/range algorithm, or
parallel literal candidates with a compiler-derived state bound. Evaluate
the time and charging tradeoffs: scanning every literal is not the current
binary-search algorithm. Define state per queried predicate, not one global
compare position. Gate long-prefix enums and regexps on keys explicitly.

### 7. [major] Embedded validation needs bounded subwindows and simultaneous observers of the same bytes

**Where:** §§17.1–17.2; program.md §8.4.

For `(bstr .cbor T) / h'…long literal…'`, an embedded walker and an outer
literal comparison observe the same content. For an intersection with
`.bits`, both predicates must see it. A nested `.cbor` starts another
bounded document inside that range. Replacing a global window/end/counter
when entering the inner document loses outer state; running the outer scan
only after the inner one needs replay that a stream cannot provide.

Also, `bstr .cbor uint / bstr` must accept the byte string containing `ff`.
The embedded `indefinite` is local, not a terminal source or outer-profile
failure. Its remaining bytes must still reach any surviving outer observers.

**Fix:** specify a document-context stack: absolute content start/end,
physical frame depth, local depth/items/top/cose settings, query results and
local witness/error state. Clip each logical subwindow to its enclosing
document end even when the supplied window extends beyond it. Inner EOF is
the byte-string end, not source EOF. Dispatch content once to all required
observers or retain it for a stated bounded replay strategy. Restore outer
counters and witnesses on every success, failure and suspension path; only
the budget is global. This needs a worked nested example before VM coding.

### 8. [major] Deferred tag checks need summaries, and pending semantic failures must not short-circuit children

**Where:** §17.2; scanner tag table; kin/scan.kin and kin/tags.kin.

The current scanner reopens exponent/mantissa/shape/data spans after walking
the complete inner array. Those spans may be far outside the new window.
For example, tag 40 can have a tiny shape followed by megabytes of data.
Retaining a position alone does not make `shape-ok` resumable.

`c4 82 00 ff` has an invalid decimal exponent, but the baseline reports
`indefinite` from the mantissa. Likewise `d8 28 82 80 81 ff` has invalid
shape but reports the data child's `indefinite`. Both were exercised locally.

**Fix:** gather per-active-tag summaries while walking: decimal exponent
admissibility, mantissa kind/nonzero/modulo-10 information (including the
negative integer adjustment); ndarray shape kind/count/positive dimensions
or an overflow-safe product summary, and data kind/element count. Save a
pending semantic-invalid flag, then finish the children and perform the
semantic decision in scanner order. Invalid components may themselves be
arbitrarily large legal containers; keep the invalid flag and still walk
them. Nested tags require nested summaries. Charge their scans and include
them in scratch. There is no need to retain the entire inner array.

### 9. [blocker] One shared scratch per isolate becomes corrupt across `await`

**Where:** §17.1 versus architecture §8 and program.md §§12–13.

Validation A suspends on a range read. Validation B starts in the same
isolate and reinitializes the shared scratch. A resumes into B's frames,
epoch marks, path and budget. A single JS thread does not prevent this
interleaving. A synchronous `read` implementation can also reenter public
APIs before returning.

**Fix:** lease exclusive scratch for each live session, from start through
success/failure/abort, including while it awaits input or scheduling. A pool
may reuse only idle arenas. Bound active sessions and pooled high water;
immutable Programs may still be shared. Reject concurrent resume/feed of
one session. Rust should own its state across `Poll::Pending` and expose
borrows only within a resume; do not retain a borrow of the old input window
after it is released. The synchronous buffer API can retain a simpler
exclusive, short-lived lease.

### 10. [major] Budget identity must include charge timing, not just final totals

**Where:** §17.4; program.md §14; SPEC §7.

Under the existing promise, yes: for identical bytes, Program and effective
limits, logical budget behavior **must be independent of window boundaries**.
`ceil(128/64)` is two units whether a scan sees 128 bytes at once or 128
single-byte chunks. Summing `ceil(chunkLength/64)` would charge 128 units.
Reentering a head must not count its item, initialize its container or charge
its query twice.

The harder case is ordering. The current schedule charges entire scans and
binary-search probes in walk order. A streaming implementation may interleave
UTF-8, literal, regexp and embedded work that the contiguous driver performs
sequentially. Equal final totals do not imply equal failures at a nearly
exhausted budget. Computing a predicate speculatively and charging it much
later can also do substantial work after the effective budget was consumed.

**Fix:** define semantic charge events and their commit points. Persist a
scan's charged extent/remainder and the “already charged” state of each
pending operation. Either preserve the normative schedule, or revise it for
both drivers with an explicit decision and new expected counts. Record the
item's absolute start for budget offsets; do not report the current chunk
cursor. Keep I/O requests, cache misses and scheduling yields outside this
logical budget, since those depend on source policy. Bound them separately
by bytes/requests/in-flight work/deadlines. Add copying, tag summaries and
other new input-dependent loops to the bounded-work accounting.

### 11. [major] Profile continuation and witness state must survive suspension independently

**Where:** §17.2; architecture §4.5; program.md §9.2.

If the first element of `[uint, any]` is text, save its schema failure and
continue checking the rest. If a later window contains a bad map key, the
profile error wins. If the later content is valid, the original witness wins.
If the later walk exhausts the budget, `budget` wins. A stream driver must
not expose the early schema failure as its final result.

**Fix:** make live/dead/profile-only mode, pending witness, its path depth,
extra segment and absolute offset explicit session state. Dead descendants
must continue profile checks, including key ordering and deferred tag checks,
without overwriting the frozen schema path. Store key ids/`*`, not borrowed
key bytes or arbitrary received keys. Embedded failures need their local
scope from finding 7. Carry UTF-8 sequence-start and typed-element-start
offsets across windows so errors name the original bad sequence/element,
not the next window. Test clearing a child witness when another ancestor
candidate survives, including immediately before suspension.

### 12. [blocker] A checked blob view needs an immutable snapshot, not just `{size, read}`

**Where:** §17.3 blob handles; §17.6's check-then-build for handles.

Validate object version A, evict a chunk, then lazily navigate or build from
version B of the same size. The view's “checked” certificate now applies to
different bytes. A tape from A can even point into the middle of B's items.
An LRU cache and a size recheck do not solve this. Mutation during the
validation pass itself can assemble ranges that never formed one snapshot.

**Fix:** define a handle as a snapshot of a specific immutable byte sequence,
with stable size and stable range contents for the complete view lifetime.
Adapters must pin an object version or enforce a strong version precondition
on every range, including later navigation and the builder's second pass.
Verify range position, response length and total size; reject a server's full
response where a bounded range was required. A changed/missing version
invalidates the session/view, rather than silently refreshing it.

An arbitrary hostile `read` function cannot be made truthful by this API.
Document the trusted adapter contract. For adversarial storage, authenticated
chunks/Merkle proofs or a retained verified snapshot are separate designs;
knowing a whole-object hash alone does not authenticate an arbitrary partial
read. Cached windows must also have exclusive immutable ownership while
used: a producer must not overwrite/recycle a returned Uint8Array. Apply the
same stability rule to caller-owned buffers retained across async work.

### 13. [major] Read failures and short reads are transport outcomes, not CBOR verdicts

**Where:** §17.3 JS/Rust blob interfaces.

Rust `read_at`/`Read` may return fewer bytes than requested. A JS handle may
throw synchronously or reject later. An empty read before the advertised end
may mean the object changed or the adapter broke its contract. Mapping every
such event to `cbor/truncated` falsely claims a content verdict; retrying zero
progress indefinitely hangs validation.

**Fix:** normalize adapter results to bytes/progress, confirmed end, or a
sanitized source error. Choose whether the public JS handle promises exact
reads or allows short reads; adapters must consistently implement that
choice. Accumulate bounded short reads, retry only well-defined transient
failures, and stop on no progress. A known-size source ending early is a
source-consistency failure. An actual unknown-length stream reaching EOF
mid-item is CBOR `truncated`. Define source-error and abort precedence against
pending schema/profile errors without pretending transport errors are
cross-host deterministic byte verdicts. Never attach raw rejection objects,
URLs, bodies or input bytes to public errors.

### 14. [major] A 64-bit window base does not make the existing ABI support 64-bit documents

**Where:** §§17.2, 17.6 versus program.md §§2, 12–14 and §16's tape.

Every durable location must survive window replacement: item starts,
container/embedded ends, witness and error offsets, previous-key references,
literal positions and tape entries. `out[2]` is currently one i32;
`LIM_INPUT_BYTES` and the per-call limit are one i32; tape entries are i32.
JS numbers cannot represent every u64 byte offset exactly. A large string's
length/progress and `.size` handling also cannot be repaired merely by
making its current window-relative index small.

**Fix:** select one cross-host address domain. For full u64, use hi/lo in
kin and BigInt or an explicit pair at the JS boundary; otherwise explicitly
cap both hosts to a common exact domain. Specify checked additions,
subtractions, range ends and conversions, including `offset + length`
overflow and windows smaller than 2^31. Never truncate or round an offset.
Reconcile all limits, size predicates, output slots, tape and cache keys.
The same effective input limit should apply to the same logical document on
every source; a handle should not silently raise it.

The claim “Program unchanged; only scratch amended” is premature: compiled
limits, source-key preimage, derived scratch requirements and any new key
policy need a version/compatibility decision under D025. Reserved words do
not by themselves authorize a semantic format change. Keep the existing
<2^31 domain for the first slice; 100 MB already fits it.

### 15. [major] Cache, read-ahead and zero-copy lifetimes need a byte-based contract

**Where:** §17.3's default 16 × 64 KiB LRU; §16 accessors.

Sixteen chunks is not a memory bound if reads can return oversized arrays,
pinned views prevent eviction, or read-ahead has unlimited in-flight requests.
One MiB per handle also scales poorly across many idle handles. Retaining a
one-byte subarray can retain a very large backing ArrayBuffer.

**Fix:** begin with one bounded sequential window and no read-ahead; add a
measured cache for navigation. Specify maximum resident and in-flight bytes,
maximum request size/concurrency, range alignment/coalescing, duplicate-read
coalescing, idle-cache release and scope (per handle or shared). Pin leased
windows explicitly; define what happens when pins exhaust the cap. Do not
reuse bytes behind returned zero-copy views. Either return owned copies or
require an explicit lease whose cost is charged to the cache budget.

Remote accessors also cannot uniformly keep §16's synchronous `.text()`,
`.get()` and `.raw()` surface. Choose a separate async view/cursor surface,
or an explicit ensure/prefetch then synchronous leased-window API. Do not
turn the buffer path into a value-or-Promise API on every access. An absent
map key can require scanning the entire map without a previously built
index; a few requests is a workload-dependent outcome, not a guarantee.

### 16. [major] Backpressure is more than pausing reads while the VM executes

**Where:** §17.3 stream strategy and `feed`.

A fast producer can enqueue unbounded chunks while the VM awaits a slow
consumer or scheduler. Conversely a single supplied 100 MB chunk defeats
the stated small carried-memory bound if its unconsumed tail is retained.
Taking a subarray does not release the original backing store.

**Fix:** pull only when there is input capacity **and** output capacity, with
bounded prefetch and an explicit maximum accepted chunk/queued-byte policy.
The push API must report consumption and refuse/reject concurrent feeds
until it is ready. Bound pending builder events too. State separately the
VM's owned memory, borrowed current-window memory, adapter queues and the
upstream source's own buffering; the library cannot bound arbitrary producer
allocations. Do not repeatedly concatenate the accumulated input to obtain a
window. Exercise a fast producer, slow consumer, empty chunks and a very
large caller-owned chunk in the gate.

### 17. [major] Fused stream decode needs an output protocol and an honest memory limit

**Where:** §17.3 stream decode; D017 amendment.

Keeping built values private until success is compatible with refuse-before-
use, but an input-byte cap is not a literal bound on host heap bytes. Arrays
of tiny integers, object properties, Unicode strings and wrappers expand;
many tiny string fragments can create excessive allocation or quadratic
copying. An invalid final byte can arrive after almost the entire output
graph was built. The VM also currently promises never to call host code, so
“build while validating” needs a mechanism, not an implicit callback.

**Fix:** design bounded output batches or explicit emit/suspend states with
clear span lifetimes, consumed positions and resume acknowledgements. Keep
accept/refuse in kin. Use private trusted builder factories; do not invoke
user constructors/observers on tentative values. Document memory as
VM/source state **plus the materialized result**, and set an independent
build-allocation cap or conservative bound from bytes/items/entries. On
failure or abort release all tentative values. Build large text/bytes with
bounded copying, not repeated immutable-string appends. Validation-only
streams should remain usable without the builder and its memory cost.

### 18. [major] A forward cursor cannot provide arbitrary checked navigation after the pass

**Where:** §17.3 “What is possible” and forward-only rules.

A cursor that returns a field before the root/document end is known has
returned tentative data. A cursor that waits for complete validation has
already discarded that field. An offset tape cannot recreate those bytes.
Sorted `get` calls help traversal but do not repair this trust/lifetime
problem, and “events” must not implicitly bypass profile §5.

**Fix:** advertise precise capabilities: tentative/trusted forward events;
checked extraction of selected fields retained privately until verdict;
or checked random access after spooling to an immutable handle. Arbitrary
post-validation navigation requires retained storage. `up()` can restore
structural context, not unread a child; `at(i)`/`get(k)` behind the consumed
position fail explicitly. `raw()`/`bytes()` on streams must mean a leased
current span, a copy, or streamed chunks, never a durable zero-copy span over
discarded windows. Indexing and seeking are separate capabilities.

### 19. [major] `NEED` is not a CPU scheduling boundary

**Where:** §§17.1, 17.4; Workers constraint in architecture §1.

A fully resident window may contain hundreds of thousands of items or an
expensive regexp. It never produces `NEED`, so an async wrapper can still
block for the entire validation. A chain of already resolved Promises can
also keep running without the intended event-loop fairness.

**Fix:** add a non-error scheduling `YIELD` based on a deterministic work
quantum, separate from the global semantic budget. Resume quotas must not
alter verdicts or budget offsets. Place safe points in long content scans,
regexp work and other expensive loops, not only item boundaries. This also
makes abort responsive inside a huge string. The host schedules actual
tasks as appropriate; kin never waits or blocks on a Promise.

For the stated 100 ms Worker CPU envelope, measure both maximum uninterrupted
resume work and total request CPU. Do not assume waiting for I/O or yielding
resets that CPU allowance. A per-resume quota provides fairness; the global
budget still controls total work. Keep “resumable at item boundaries” as a
minimum public milestone, not a restriction against essential mid-string
suspension.

### 20. [minor] Preserve synchronous reads without putting source polymorphism in the byte loop

**Where:** §§17.3–17.4 JS/Rust adapters.

Unconditionally `await`ing every cache hit adds a Promise/microtask boundary
even when `read()` returned bytes immediately. One-byte inputs make this
dominant. Mixing buffers, files, network handles and streams through one
polymorphic source call in a hot loop can also defeat the stated fast path.

**Fix:** normalize source adapters once, keep the buffer entry point direct,
and keep all source calls outside the VM at `NEED`. A stable host pump should
drain available/cache-hit/synchronously returned bytes within its CPU
quantum, then await only an actual async result. Normalize allowed Promise/
thenable behavior at the boundary; do not access arbitrary source objects
per byte or per item. Make the async public operation consistently async,
while its internals avoid an await for every synchronous cache hit.

Rust's blocking `Read` belongs in a blocking driver, never directly in an
async executor poll. The async driver should retain session/partial-read
state across `Pending`, bound work per poll, and use an explicit AsyncRead
ecosystem adapter rather than claiming one universally interchangeable
trait. `read_at` for random access is a distinct capability. Do not hold a
cache lock across a read/await. Benchmark these paths independently.

### 21. [major] Terminal states, cancellation and sequence framing are missing

**Where:** §17.3 API.

An aborted range read can resolve later and incorrectly resume a reused
scratch arena. A stopped stream can keep a reader locked or an async iterator
alive. A long-lived stream of CBOR messages never reaches EOF, so the current
“return only when the stream ended” cannot deliver any message.

**Fix:** specify an idempotent abort/close lifecycle, terminal-state checks,
request generation tokens, and cleanup of scratch leases, cached windows,
read-ahead and tentative output. Cancel pending reads where supported,
release stream locks, call iterator `return()` as appropriate, and ignore
late results. Check abort at bounded work intervals as well as I/O boundaries.
Document source ownership and whether the driver may close/cancel it.

Keep single-document mode strict about trailing bytes. If wanted, add an
explicit RFC 8742 CBOR-sequence mode, not an accidental fallback: validate
each top-level item as a message, release it only after that message's full
profile/schema checks, and report an incomplete final item at sequence EOF.
Define per-item versus whole-stream limits/budgets, item index and absolute
offsets, top/cose options, and output backpressure. Previously committed
messages cannot be revoked if a later item fails. `.cborseq` inside a bounded
byte string remains a separate schema feature. Sequence support can wait;
the first API should at least leave framing explicit.

### 22. [major] The differential gate is necessary even with one driver, and random splits alone are insufficient

**Where:** §17.4.

Two drivers agreeing can share a bug. One driver can fail to resume correctly
even if specialization is never needed. Random chunks of at least one byte
do not exercise EOF at every prefix, empty feeds, `Pending`, overlapping
windows, failed reads, or suspension immediately after a charge.

**Fix:** require the gate for every resumable implementation. Compare codes
to cbor.mjs, and CDDL verdicts to the independent oracle on its supported
subset; compare paths/offsets/budget/items across generated JS, debug Rust,
wasm as applicable, and recursive/resumable drivers. Enumerate every single
cut for small adversarial inputs and all partitions for very short ones;
add seeded random/adversarial partitions for large inputs. Truncate at every
prefix and signal EOF explicitly. Probe budget limits at every relevant
charge boundary, including one unit either side, and vary scheduling quanta.

Required cases include long common-prefix keys/enums, nested retained keys,
split UTF-8/noncharacters, split typed NaNs, split bignums, deferred tag
failures, nested `.cbor` with surviving sibling leaves, schema failure then
profile failure, and witness clearing/freezing. Assert monotonic stream
consumption, no backward source reads, no double charge/emission, bounded
memory and eventual progress under valid fulfilment. Exercise malformed
fulfilments, cache eviction/version changes, interleaved sessions and abort.
Use synthetic sparse/range sources for offsets around 2^31, 2^32 and the
chosen JS ceiling when wide offsets are implemented; do not allocate those
objects just to test arithmetic. Keep out-of-bounds traps/debug overflow
checks. Passing a finite gate is evidence against drift, not proof that two
drivers “cannot drift”.

### 23. [minor] The 15% rule is a useful trigger, not a sufficient architecture decision

**Where:** §17.4; bench/SCAN.md.

The existing measurements already show sensitivity to helper size/inlining
and shared-machine noise. They also show a 1 MiB byte-string validation at
about 0.9 microseconds: that scanner skips its content. It does not measure
incremental literal/UTF-8/regexp scanning, VM query state or suspension-heavy
work. An average ratio can conceal a severe regression on tiny requests or
on one hostile case. A scanner-only result cannot settle the VM decision.

**Fix:** retain 15% as a provisional review threshold on explicitly named
per-workload medians with repeat-run uncertainty. Report absolute latency,
tail/max resume cost, code size, scratch and maintenance cost too. Retake the
decision on the VM workloads; avoid committing to two complete walkers solely
because one noisy tiny benchmark crosses 1.15. Prefer specialization of a
small input/head loop before duplicating the state machine. The same Program
is a good invariant; the same control-flow implementation is not mandatory.

### 24. [note] The benchmark plan needs to separate VM overhead, transport policy and retained output

**Where:** §17.5.

**Fix:** use paired runs with identical bytes, schema, options and verified
answers, and report at least the following matrix:

A simulated 100 MB remote object exceeds the default 1.5 MB message cap;
state the raised limit and valid item/entry counts. Distinguish checked full

Inject latency only for actual cache-miss reads, bound read-ahead, and include

## Recommended first slice

1. **Freeze the session contract first.** Specify known length/end, window
   ownership/consumption, `NEED`, scheduling yield, finalization, abort,
   exclusive scratch and source errors. Keep offsets and documents below
   2^31 initially, with the existing 1.5 MB default. D027's source goal does
   not require >2 GiB support to establish the abstraction.
2. **Build the resumable profile scanner in kin**, keeping the recursive
   scanner as oracle/yardstick. Support split heads, mid-string stops,
   nested maps and tag summaries. Preserve the current accepted language:
   no new 1 KiB/64 KiB mandatory key cap. For the bounded first slice, a
   preallocated source scratch arena bounded by configured max input bytes
   can retain active key spans; account for it explicitly. It is bounded
   memory, but not the claimed tiny input-independent carry. If that cost
   is unacceptable, first slice the random-access source and defer general
   forward-only maps rather than silently narrowing the profile.
3. **Exercise three simple supplies:** a direct buffer, an immutable
   in-memory synchronous range handle with one window, and a push source
   with an exact declared document length plus explicit finalization. Reject
   mismatch between promised length and delivered bytes as a source failure.
   Add a genuinely async mock and interleaved sessions before real adapters.
   This establishes streaming within messages; it does not yet claim the
   unspecified unknown-length error behavior has been solved.
4. **Run the split/EOF/lifetime gates and measure the matrix's first three
   rows.** Resolve unknown-length refusal semantics before accepting a general
   unframed ReadableStream. Use the scanner result to inform, not permanently
   settle, the 15% choice.
5. **Then amend the VM scratch/API/charging specification**, with worked long
   `LITSET`, key-typeset and nested-EMBED executions. Add validation-only
   source support against the same Program. After that, add one snapshot-safe
   asynchronous blob adapter and measure whether any cache/read-ahead helps.

Defer fused stream materialization, arbitrary remote views/tape, automatic
LRU/read-ahead, sequences and wide offsets until their contracts and measured
benefits justify them. This leaves a small, useful and reviewable D027 core:
one byte-level decision procedure, suspension with no I/O in kin, exclusive
session state, and a direct buffer path whose cost is actually measured.
