# Independent review of architecture §16

2026-10-29. Scope: D026 and the proposed cursor, views, tape, subtree
validation and writer. Read AGENTS.md, SPEC.md, all of architecture.md,
DEVLOG.md including D026, program.md, scanner.md, the read-only Bindle CBOR
profile, the JS host, and the generated JS scanner. References below are to
those local documents and implementations. These are recommendations for
the provisional design, not new owner decisions.

The three opening modes are a useful starting point. The major problems are
the lifetime of a validation result over mutable bytes, the meaning of
position-aware validation, and an index whose addressing and construction
are not yet specified. Fix those contracts before freezing an API or tape.

## Numbered findings

### 1. [major] Separate the trust guarantee from the indexing policy

**Where:** §16.1–16.2.

Checked and trusted opening are different trust contracts; an index is an
independent performance choice. Checked without a tape still inspects every
item for profile and schema validity. It saves materialisation, not the
initial validation walk. Conversely, trusted bytes could use a previously
built index, or build a container index on demand. Three named presets are
fine, but they should not become three separate parsers with subtly different
semantics.

“Its own storage” is not sufficient evidence of validity. A truncated write,
an older profile, a different `cose` setting, or changed bytes invalidates that
assumption. Tooling that deliberately inspects malformed bytes has a weaker
contract again. No sequence of successful lazy accesses establishes that the
whole document satisfies profile §5.

**Proposed fix:** model trust/validation and indexing separately. Keep the
default a full profile check, with optional schema checking. A trusted opener
requires an explicit caller promise about these exact bytes, profile/options
and lifetime. If inspection of malformed input is supported, specify which
structural guarantees it provides and keep its results visibly unverified.
Only a successful full check promotes a message to checked status. Preserve
the whole-message-before-use rule for RPC, even when a handler needs one
field. Scope “canonical span” claims to checked, stable bytes or to the
trusted caller's explicit precondition.

### 2. [blocker] A checked view has no lasting proof without byte ownership

**Where:** §8 and §16.4; `host/js/src/scan.mjs` and `build.mjs`.

The existing synchronous scan-then-build protects against shared input and
copies byte/typed-array values. A persistent view changes that argument:

```js
const b = encode({ a: 0 });
const v = view(b, { schema });
b[b.length - 1] = 1;       // possibly outside the schema's allowed range
// v now reads bytes that its validation never approved.
```

Changing a container head can also invalidate every saved tape offset. A
copied input does not solve the problem if `raw()` or `bytes()` exposes its
backing buffer: a subarray's `.buffer` lets the caller construct a view over
the entire message and rewrite heads or unrelated siblings. Freezing the
wrapper does not make the buffer read-only. Returned writable typed arrays
create the same problem. Buffer pools, detachment/transfer and resizable
ArrayBuffers add lifetime hazards. SharedArrayBuffer permits mutation even
during a single read or validation.

**Proposed fix:** define two explicit ownership contracts. A safe owned mode
snapshots input into private storage and returns copies from APIs that expose
writable bytes. A borrowed zero-copy mode requires the caller to keep the
entire backing store stable and attached while any view, cursor, iterator,
raw span or index exists; exposing aliases is part of that contract. JS
cannot enforce a read-only `Uint8Array`, so do not advertise the borrowed mode
as an enforced immutable capability. Reject shared backing stores in the
borrowed checked mode. To support shared input safely, copy first and
validate the private copy; never validate shared bytes and then copy them.
Define handling of resized/detached input without leaking native exceptions
or trusting stale offsets. Rust can express a stable borrow more strongly;
JS needs the documented contract or the copy.

### 3. [blocker] A literal key does not identify one value typeset

**Where:** §16.3 versus program.md §7 and §8.3.

The Program's key index maps a key to `(owner factor, naming records)`, and
each naming record identifies an alternative and literal entry. It is not a
key-to-typeset function. Query construction depends on live map leaves,
alternatives, residual pools, key-typeset matches and cuts.

For example:

```cddl
r = { a: 0, x: uint // a: 1, x: tstr }
```

In deterministic order, `a` precedes `x`. For `{a: 0, x: "s"}`, the second
map leaf has already died before `x`. Unioning every entry named `x` admits
`tstr`, although the full walk queries `x` with `uint` only and rejects it.

Literal entries alone are also incomplete:

```cddl
r = { ? (a: uint, b: uint), * tstr => any }
```

`{a: false}` is accepted: the empty factor alternative survives through the
absorbing residual. Looking up the literal entry for `a` and validating only
against `uint` incorrectly rejects it. This is exactly the ABSORB interaction
represented in program.md §15.5. Conversely, in
`{ ? a: uint, * tstr => any }`, the implicit cut on the one literal entry can
kill that alternative even if the residual's `any` matches the value.

**Proposed fix:** withdraw the unconditional direct-map-typeset claim. A
direct projection is an optional proven fast path, for example a single
unconstrained context with a unique applicable entry and no competing
residual. In general reproduce the VM's key/query/state rules, or explicitly
offer a conservative union with weaker meaning. That union must include
applicable key-typeset entries and ABSORB predicates, not just named entries.
Do not report it as the full walk's exact query.

### 4. [blocker] Define what subtree `validate()` actually proves

**Where:** §16.3, especially “exactly as the full pass would”.

Even reproducing the exact prefix query does not establish that the subtree
fits an eventual successful parent:

```cddl
r = { kind: "a", x: uint // kind: "b", x: tstr }
```

`x` sorts before `kind`. On `{x: 1, kind: "b"}`, the full VM queries `x`
with both value types and its uint leaf matches. The later discriminator
kills the remaining alternative, so the message fails. A successful
`get("x").validate()` can therefore coexist with a failed root even when it
uses precisely the query the full walk used. Missing siblings and final
occurrence minima provide simpler examples. The same distinction applies to
an element of a homogeneous array whose overall length is wrong.

There are at least three possible operations: validate a detached span
against an explicit type; evaluate it against the candidates reachable at
this prefix; or establish compatibility with the actual enclosing document.
The last can require siblings on both sides, final counts, and ancestor
checks. A union over all alternatives is only a local overapproximation; it
does not prove that any complete enclosing message can succeed.

**Proposed fix:** give the first two operations distinct, precise contracts
and reserve root validity for a full validation. For an implicit positional
operation, return/retain candidate match information and label its result as
local, not as a root schema certificate. Exact enclosing-document validity
should validate the root, or use a previously established root result. State
that local failure selection, budget use and profile-error precedence need
not equal a whole-message invocation: an unseen later profile error cannot
win locally. Never let “validated field” imply safe RPC dispatch by itself.

### 5. [major] Child projection must preserve ancestor predicates

**Where:** §16.3; program.md §5 and §8.4.

Maps and array transitions are not the only ways a parent constrains a
child. Consider:

```cddl
r = [uint] .and [0..3]
```

For `[8]`, the child matches `uint`, but the parent intersection fails. A
plain union of the two child types loses the conjunction. A whole-container
`LIT`, `.ne`, or another same-item predicate need not have a useful independent
child type at all. Dependency-only leaves must not accidentally become
successful answers. Tags constrain their contents; `.cbor`/`.cborseq` create
separate document scopes rather than ordinary byte-string children.

**Proposed fix:** distinguish candidate leaf evaluation from acceptance of
the expression that requested it. Preserve a continuation/provenance
structure if positional validation promises ancestor semantics, or refuse
implicit projection for these shapes and require an explicit subtree type.
Reuse the Program's answer/dependency distinction. A successful checked
root need not have a unique successful branch, so even there “the type at
this position” may remain a set rather than one type.

### 6. [major] Prefix evaluation needs a bounded API and a scratch argument

**Where:** §16.3 versus program.md §10, §12 and §13.1.

Skipping heads cannot advance a heterogeneous array automaton. In
`[? uint, tstr]`, deciding the candidates at the second element requires the
first element's matching result. For `[* T]`, the direct query is safe only
while that parent candidate is live; a prior element that failed T has
already killed it. Counted homogeneous positions also have an end/min/max
obligation. Maps have analogous prefix state, in addition to lookup offsets.

The frozen VM entry point accepts a rule and a whole input, not an arbitrary
query list, span and starting context. Restarting at a child as a new root
can incorrectly allow COSE integer keys in a nested map, reset depth, reject
a scalar because `top` defaults to map, or let a truncated embedded item read
past its byte string. Its frame sizes come from the rule's closure chain at
the original physical depth, not necessarily frame zero.

**Proposed fix:** first specify an internal span-evaluation interface:
`[start,end)`, original physical depth/document scope, root rule/closure
chain, answer/dependency query, inherited `cose` context, limits and explicit
budget policy. End-bounded helpers already exist in the generated scanner;
reuse them. Exact consumption of the span is mandatory. Copy any persistent
query/continuation state out of shared scratch, or recompute it on demand.
State the cost of prefix replay and cap it. Treat changes to the frozen
Program/VM contract through D025's change process; §16 does not already
supply this interface.

### 7. [major] The lazy local-check list omits conversion-critical checks

**Where:** §16.2; scanner.md's complete refusal table.

Shortest heads, lengths, depth, decoded text and floats are insufficient.
An accessor also needs to handle/refuse reserved additional information,
indefinite forms, disallowed simple values, key types and COSE label bounds,
unsupported tags and tag content shapes. Specific examples:

* `c2 41 01` is not a valid bignum; it cannot become `1n` through a trusted
  builder fast path.
* `c4 82 20 0a` has a mantissa divisible by ten and is not a normalized
  decimal. Exponent range, nonzero mantissa and integer/bignum form matter.
* `d8 55 44 00 00 c0 7f` is a float32 typed array containing NaN. A generic
  zero-copy typed accessor must not silently expose it as profile-valid.
* Tag 40 requires valid dimensions and a checked product equal to the data
  count. A valid shape alone is insufficient.

Tag structure needs an explicit policy. A tag structurally wraps exactly one
item. The supported profile tags have more restrictive content forms:
bignum and typed-array tags require bytes; decimals and ndarrays require a
two-element array. Direct tag-on-tag chains must not be admitted merely
because their generic structure can be skipped; the profile's allowed
bignum mantissa and ndarray typed-data nesting occurs inside those arrays.
A generic “skip tag head, then skip one child” must not be confused with
proving those semantics. NaN scans for float arrays and
UTF-8/noncharacter scans for text remain proportional to payload bytes when
actually checked; length-prefix skipping is O(1), checking is not.

**Proposed fix:** define a structural skip operation separately from a
profile-check/materialise operation. Every lazy accessor that promises a
profile value must run all checks needed for the item it converts, in kin,
including its tag semantics. Reuse scanner rules rather than writing a
second abbreviated validator. Do not call the unchecked `build()` on a lazy
subtree until a complete scan of that exact span has succeeded. Decide
whether lazy map iteration checks values as well as keys, and document it.

### 8. [major] Checking keys already visited cannot justify ordered search

**Where:** §16.1–16.2.

For `a2 61 62 00 61 61 01` (pairs `b:0, a:1`), a search for `a` can stop
at `b` and falsely report absence. For `a2 61 61 00 61 61 01`, returning the
first `a` misses its later duplicate. Checking adjacent keys while searching
does not detect an invalid suffix. Binary search over lazily collected pair
offsets has the same prerequisite. Invalid maps that are merely skipped
remain invalid even if their structure can be traversed safely.

**Proposed fix:** early exit and binary search require an independently
established sorted-and-unique invariant, either from the trusted caller or a
complete scan of all keys of that map, structurally skipping values. Cache
that fact only over stable bytes. For unverified inspection, scan the whole
map before promising a unique lookup/absence, or explicitly disclaim that
promise. No local search can establish profile §5 for unsearched maps.

### 9. [major] Lazy traversal needs a structural safety and resource contract

**Where:** §16.2 and §16.6.

`82 00 81` has a readable first array element and a truncated second element.
The root's minimum remaining-byte check passes, so `at(0)` can succeed before
the defect is discovered. Trailing bytes are similarly unknowable until the
root end is found. This is acceptable only under the advertised weaker
contract, and it prevents whole-message canonicality/validity claims.

A navigation operation must carry the original depth; resetting depth at
each `enter()` lets a deep chain evade the bound. Counts and work also need
bounds during structural skipping: “not semantically checked” must not mean
unbounded recursion or loops. Repeated independent lookups cannot establish
the document's total item count without traversing it. Conversely, charging
the global profile item counter again for each revisit would reject a valid
message merely because it was read twice.

Overlapping spans are not an extra feature of valid CBOR: children partition
their container contents. They become a bug if lengths are checked only
against the backing buffer, a cached index survives mutation, or arithmetic
wraps. A supplied end offset from an unverified index is not a proof.

**Proposed fix:** every structural operation enforces progress and bounds:
`parentStart <= childStart < childEnd <= parentEnd <= inputEnd`, consecutive
siblings meet without gaps/overlap, and completed containers consume exactly
their declared children (twice the pair count for maps). Use checked
subtraction-based length tests, depth limits and bounded work. Define
per-operation traversal budgets separately from document validity limits;
offer an aggregate session budget if needed. A malformed lazy input yields
only a bounded local failure, never a claim about the unvisited suffix.

### 10. [major] The tape lacks the addressing needed for its complexity claims

**Where:** §16.2's tape paragraph.

An end-offset word indexed by preorder ordinal plus child *byte* offsets is
not yet a usable constant-time index. Given a child's byte offset, how is
its preorder ordinal found? Given a container ordinal, where is its
contiguous child table? Neither relation is supplied. Searching another
directory can be reasonable, but it changes time and space claims. A map
also needs access to the value of the selected pair, not just its key.

For `[[0],1]`, an end-offset tape contains repeated ends for the inner array
and its scalar. End offsets alone do not identify starts or child-table
locations. An implementation could add records or encode these relationships
implicitly, but the full layout and its navigation algorithms must show it.

**Proposed fix:** specify node handles, byte versus ordinal units, table
location, start/end recovery, empty containers, map key/value addressing,
tags and maximum offsets before asserting the bound. Give a small worked
layout for nested arrays/maps and demonstrate each operation. Account for
all directories, sentinels and container records, not just the two principal
arrays. Keep a tape as a private, derived structure tied to one message;
do not accept caller-supplied tape offsets as trusted evidence.

### 11. [major] Exact sizing conflicts with writing the tape in the counting pass

**Where:** §16.2; program.md §13.1.

The final item count is known only at the end. The VM cannot both allocate
exactly that many words first and fill them on the one pass that discovers
the count. Its frozen interface has no tape argument and promises no
allocation or host calls. Even if a parent supplies a child count, descendant
counts remain unknown. Reserving arbitrary declared counts before checking
remaining bytes would reintroduce length-bomb allocations.

**Proposed fix:** choose and describe one policy: caller-provided bounded
capacity (possibly the item-limit maximum), a count/check pass followed by an
exact index pass, or bounded growth/slabs with explicitly reported allocation
and peak memory. At default limits, a 1 MiB reservation per indexed message
may be acceptable, but it is not exact sizing. Avoid host growth callbacks
inside validation; they undermine the no-callback/shared-scratch argument.
On any validation/index failure, discard the unpublished partial index.
Specify capacity exhaustion and allocation failure independently of CBOR
validity. Define indexing charges and whether the validation budget remains
identical with indexing enabled; don't silently change the frozen schedule.

### 12. [major] “Items” has several incompatible meanings for the tape bound

**Where:** §16.2 versus scanner.md and program.md §8.4.

The profile counts a typed-array or bignum tag as one item; its byte-string
content is not counted. Yet a generic navigable CBOR tree has a tag node and
a byte-string child. For an array of m empty typed arrays, the profile count
is `m+1`; a tape recording both nodes has `2m+1` nodes. One end word per node
plus one child reference per edge already exceeds `2 × profileItems`, before
directory overhead. Decimal and ndarray inner arrays *are* counted. Embedded
documents reset the scanner counter and can be parsed as extra schema
children; their index entries cannot be bounded by the final outer count.

**Proposed fix:** distinguish profile item count, physical/synthetic indexed
nodes, and all embedded-document nodes. Either make bignum/typed tags atomic
in the tape and derive their content spans directly, or budget their extra
records. Treat byte-string contents as opaque in the outer tape; optional
embedded indexes need separate scope and an aggregate memory cap. State the
bound with its exact counting convention and metadata allowance. “8 bytes
per item” is a target for one representation, not a demonstrated total.

### 13. [minor] Choose an index from access patterns

**Where:** §16.2 and Phase P5.1.

The dense tape can be good for repeated random navigation of an item-heavy
tree. It adds little to a large byte string or typed array whose end is
already computable from the head. A map/array-only direct-child directory
can omit scalar end records; neighboring child boundaries can give spans,
with an explicit container-end sentinel and a way to locate nested tables.
That may save memory, but container records and indirection still count.

Useful alternatives to benchmark are:

| Policy | Benefit | Cost to expose honestly |
| --- | --- | --- |
| No persistent index | Minimal retained memory; good for one field or sequential iteration | Repeated random lookup rewalks content |
| Dense direct-child tables for all containers | Fast random access after one build | All child offsets plus container addressing metadata |
| Index one container on first demand | Pays only for accessed containers | First access scans that container; cache memory and eviction |
| Sample every k children/pairs | Smaller directory, tunable tradeoff | Up to k sibling skips; a skipped sibling may itself have a huge subtree |
| Ends for selected subtrees | Speeds costly structural skips | More state; scalar ends are often redundant |

Without an index, a “linear key scan” can also walk the descendants of every
preceding value. Repeated `at(i)` from the array start costs O(n²) even for
scalars. A sequential iterator/cursor must retain its next position rather
than implement iteration as repeated random access.

**Proposed fix:** keep the first implementation private and benchmark k =
8/16/32 and a lazy per-container directory against a dense design. Report
first-access and repeated-access costs separately. O(k) *siblings* is not
O(k) bytes or heads without additional end information. Map lookup is
O(log n) comparisons, not constant-cost comparisons: long encoded keys still
cost bytes. Do not add delta/varint compression or succinct-tree machinery
before a measured need justifies decoding/rank/select complexity.

### 14. [major] Persistent state cannot borrow the per-isolate scratch

**Where:** §8, §16.2–16.4; program.md §12.

The statement that a tape must outlive validation is right. The same is true
of any saved query, candidate alternatives, array prefix state and cursor
stack. A second view validation can overwrite shared scratch before the
first view is used again. Generators interleave between `next()` calls, and
two cursors can coexist even in a single JS isolate. Shared scratch is safe
only during a synchronous, callback-free operation, not across yields.

“Nothing is allocated beyond the view object” also needs narrowing. A mutable
cursor requires O(depth) navigation state; immutable descent creates view
objects; an iterator creates state, and `[k,x]` creates tuples and child
views. `subarray` is zero-copy but still creates a JS wrapper. A small
retained subview keeps its entire backing buffer, and often its parent tape,
alive. Many simultaneous views cost the sum of their inputs and indexes,
not one shared scratch arena.

**Proposed fix:** separate transient VM scratch, message-owned persistent
indexes, and per-cursor traversal state. Reborrow scratch for each bounded
operation and copy only deliberately retained state. Define input/tape
retention, optional cache caps and release semantics (including surviving
child views). Specify whether advancing a mutable cursor invalidates saved
handles; never yield the same mutable cursor as though it were a stable
view. Benchmark tuple/view allocation and GC against cursor traversal.

### 15. [major] Map permutation needs ownership and offset rules

**Where:** §16.5.

Sorting complete `[encoded key || encoded value]` ranges at map end is
sound: a completed nested value's encoding is self-contained. For an outer
map whose `z` value is a nested map and whose `a` value is a scalar, move
the entire `z` pair after `a`; do not sort heads or fragments independently.
Nested maps must finish sorting first. Sorting outer pairs then invalidates
all absolute offsets/bookmarks retained for nested data.

The cost is not “one permutation” for the whole message. A comparison sort
of m pairs takes O(m log m) key comparisons, which can inspect long common
prefixes, plus O(Bmap) bytes copied for the map. A byte near depth D can be
copied at D enclosing map ends, yielding O(D × B) movement on nested
examples, plus sorting and buffer-growth/final-copy costs. Fixed depth bounds
bound that multiplier, but it can still matter in a Worker. Pair metadata is
O(m), and permutation scratch may approach the largest map's encoded size.

**Proposed fix:** require closed nested values, nonoverlapping complete pair
ranges and duplicate detection before publishing output. Use offsets rather
than pointers across buffer growth; expire/remap bookmarks after moves.
Do not expose output views while mutation is possible. Specify peak buffer,
pair-table and permutation memory, and cap allocation before growth.
`keysSorted` must compare encoded keys and reject equality or descent; it
must not mean “trust the caller”. Preserve a fast path that avoids copying
already sorted ranges. The current encoder sorts keys before writing values;
retain that option for materialised objects rather than forcing a large
value-copy regression through the new writer.

### 16. [major] The writer needs a grammar and failure contract

**Where:** §16.5.

Known counts make definite-length output possible, but counts alone do not
prevent misuse. Examples: `beginMap(1); text("a"); end()` has no value;
`beginArray(1); uint(1); uint(2)` overruns its count; a nested map used as a
key violates the text-key profile. Multiple roots, premature `end()`, use
after failure and unfinished output also need answers. A raw float method
must decide whether integral inputs are refused or normalized to integers;
the current generic `encode(number)` deliberately chooses integers for safe
integer numbers.

**Proposed fix:** define a bounded writer state machine with remaining
children/pairs, map key/value phase, depth/item/byte limits, root count and
sticky failure or transactional rollback. `finish()` succeeds only with one
complete root. Include typed-array/bignum special counting, decimal/ndarray
semantics and contextual COSE labels. Normalize or refuse invalid typed
arguments explicitly; never silently round bigint/decimal values. If a raw
span append API is added, require checked stable bytes under the destination
profile/context or validate before appending. No unfinished buffer may be
forwarded as deterministic output. Unknown-length container output is a
separate buffering/backpatching feature; it cannot use indefinite CBOR under
this profile.

### 17. [major] Clarify the kin/host boundary before replacing the encoder

**Where:** §16.5–16.6 versus D003/D004 and architecture §2.

The proposed navigation/profile logic belongs in kin. So do encoded-key
comparison, structural bounds, span rules, tag checks, byte-level schema
query construction and deterministic decisions over encoded numeric bits.
The host still needs to inspect JS classes, obtain bigint magnitude bytes,
turn JS numbers into bits, encode UTF-16 to UTF-8, reject host-only invalid
values, allocate/grow buffers, and expose JS wrappers. For example,
TextEncoder replaces lone surrogates; host admissibility must reject them
before that conversion loses the evidence.

Calling a wrapper “thin” does not resolve who checks writer state, host
argument ranges or output capacity. The current host owns the encoder under
D004 and contains shortest-width logic; §16 proposes moving part of that
responsibility. This is a real boundary refinement, not already accomplished
by the scanner. A host implementation of residual/prefix matching would also
duplicate the VM even if described as navigation.

**Proposed fix:** specify a small host-to-kin representation (bounded
magnitude bytes, float bits, UTF-8 spans, container commands). Keep all
byte/profile decisions and portable writer grammar in kin; keep memory
management and host-value admissibility in hosts as D003 already permits.
Pin command-stream/output equivalence and host-only refusal vectors across
targets. Propose the D004 refinement explicitly for owner disposition after
this review, without changing the frozen Program just to add host wrappers.

### 18. [major] Accessor types and typed-array alignment are API decisions

**Where:** §16.4; `host/js/src/build.mjs` and `values.mjs`.

`number()` must not round an unsafe integer or coerce a decimal. Define it
as scalar float or safe integer only; offer exact `bigint()` for integer
items and an exact decimal accessor returning the existing Decimal semantics
(bigint mantissa, negative exponent, no numeric/JSON coercion). Define
whether `bigint()` accepts safe integers as well, and refuse fractional
floats. `kind` is a wire kind: bignums and decimals are tags, so either add
a semantic kind or explicit tag/content/decimal/typed/ndarray methods.
Define lengths as bytes, UTF-8 bytes, array elements, map pairs or typed
elements, rather than leaving one overloaded property ambiguous.

Zero-copy native typed arrays are not always possible. The valid encoding
`d8 45 42 01 00` has a uint16 payload starting at byte offset 3; constructing
`new Uint16Array(buffer, 3, 1)` throws. A nonzero-offset Buffer input can
change alignment again. Native arrays use host endianness while the wire
uses little-endian. Float16Array may be unavailable. The current builder
copies into aligned storage and handles endian conversion/fallback; a new
view cannot discard those cases.

**Proposed fix:** make `typedView()` a portable accessor object using
DataView/bytes with indexed reads, with a native zero-copy fast path only
when aligned, little-endian and lifetime-safe. Distinguish it from a copied
materialising typed array. Preserve Float16Bytes, Decimal, NDArray and safe
integer normalization in `value()`. Materialised byte strings should keep
the profile's fresh-copy mapping; borrowed views are an explicit additional
API. Preserve BOM, `__proto__` safety, object-mode options and the original
COSE context when materialising subtrees. Distinguish absent map keys from
present null values and accessor type errors; errors must not echo data keys
or received values. A lookup key is not thereby a schema-named error path.

### 19. [major] “Best” needs equivalent-work benchmarks and visible tradeoffs

**Where:** §16.6 and architecture §12.

One field from 1.4 MB is useful but favors a chosen layout. A huge bstr is
cheap to skip, whereas a huge nested container is not. Repeated access can
amortize a tape; one lookup cannot. Trusted access excluding validation
cannot establish a strict-decoding speedup. Existing bench/README.md already
labels build-only measurements correctly; its scanner-unavailable status is
historical relative to the now-wired host and should not be treated as a
current full-decode result.

**Proposed fix:** use a reproducible matrix with correctness checks outside
timings and report at least:

* Full profile check; profile plus schema; full decode; checked open plus
  one field; checked indexed open plus one field; trusted navigation. Include
  first construction and repeated accesses separately, with break-even query
  counts for each index policy. Never hide snapshot/input-copy costs.
* First/middle/last/absent keys; short ASCII and long UTF-8 keys; many common
  prefixes; wide flat and deep nested values; random/sequential array
  access; 1/10/100/all selected fields; byte/typed-array versus ordinary-item
  bodies. Include small RPCs as well as 1.4 MB messages.
* View chains/iterators versus a mutable cursor; text decoding versus raw
  byte use; allocations, GC pauses, retained input/index bytes, peak memory
  and many live messages. Include defaults and explicitly labeled raised
  limits for bodies exceeding entry/item defaults.
* Writer versus generic encode with sorted/reverse/random keys, large
  nested values, long keys and duplicate rejection; sorted verification
  versus range permutation; final output copies and writer reuse.
* Invalid suffixes, duplicates at the end, malformed/truncated tags, length
  bombs, maximum-depth inputs and worst budget-bounded schemas. Report
  rejection latency and allocation, not just valid throughput.
* Cold import/first call and warmed distributions in Node and workerd,
  with native Rust/wasm costs where relevant; runtime and compiler bundle
  sizes separately. Record exact machine, OS, runtime/compiler versions,
  options, seeds, warmups, repetitions and dispersion in bench/README.md.

Use the local cbor.mjs snapshot as the strict baseline. Candidate broader
JS comparisons are **cborg**, **cbor-x**, and **cbor (node-cbor)**; these are
comparison targets, not claims about their current options or performance.
Do not install or fetch them for this review. Later pin available versions
and publish a feature/options matrix: canonical encoding, duplicate/order
checking, limits, extensions/records, number/tag mapping and copy behavior.
Where a library needs an extra profile scan, include that scan in a
strict-equivalent measurement and separately label its bare decode. Do not
compare different accepted languages as equivalent strict codecs. Check
values and canonical bytes independently, including Buffer and typed-array
cases where the baseline has known mapping limitations. Publish wins and
losses; use “best for these workloads and guarantees” rather than a universal
ranking.

### 20. [minor] Whole buffers, streaming and sequences need an explicit scope

**Where:** §16, R8 and D016.

A persistent zero-copy span assumes retained contiguous input. A network
chunk ending inside a head or text payload is incomplete, not necessarily
malformed. A sequence of CBOR items is not one profile message: accepting
the first item and ignoring its suffix would violate `trailing` and could
permit request smuggling. `.cborseq` is an embedded schema feature, not
permission for top-level concatenated RPC bodies.

**Proposed fix:** state that Phase 5 initially accepts complete contiguous
single-item buffers. Bound transport accumulation before allocation; don't
use any values until the final body passes profile/schema validation.
Streaming input may initially buffer to that bound. A resumable scanner
later needs explicit state, `need-more` distinct from final `truncated`,
absolute offsets, UTF-8/head continuation, budgets/counts and buffer-retention
rules; an explicit-stack VM is already deferred under D016. A future
sequence API must be separate, define per-item/aggregate limits and trust
boundaries, and never weaken the single-message API. An unsorted-map writer
cannot flush its map bytes before end-sort; streaming output needs sorted
keys or buffering as well.

## Review evidence and recommended gates

This was a design review, not implementation of §16. No cursor/tape/writer
prototype or performance benchmark was run, and no whole-project test pass
is claimed. No network, installation or state-changing git command was used.

An inline Node assertion script exercised existing code without creating
files. The independent corpus oracle confirmed: earlier-discriminator map
false; later-discriminator map false; ABSORB-factor `{a:false}` true; and
`[uint] .and [0..3]` on `[8]` false. The generated scanner confirmed the two
map hex examples above as `key_order` and `duplicate_key`, `82 00 81` as
`truncated`, `d8 45 42 01 00` as accepted with one counted item, and the
float32 NaN typed array as `typed_array`. Assertions also confirmed the
unaligned native Uint16Array construction throws and that existing decode
materialises a scalar independently of later caller mutation. These checks
support the examples; they do not test the proposed APIs.

Before claiming Phase 5 complete, require indexed/unindexed/root VM verdict,
code, offset and budget equivalence under the chosen charging policy;
every checked view span matching an independently parsed span; all tag/item
count and embedded-scope cases; all truncation cuts on small fixtures;
mutation/alias/Buffer/resizable/shared-input cases; concurrent views and
interleaved cursors; writer command misuse and nested permutations; and
JS/Rust identity for portable navigation/writer decisions. Include the map
and intersection witnesses in positional-validation gates. Schema errors
and API errors must retain the existing payload-free reporting rule.

## Verdict and minimal first slice for Phase 5

**Verdict: retain D026's direction; revise §16 before implementing its full
contract.** The checked view is a useful, modest extension of the existing
scanner/VM and trusted builder. The lazy positional-exactness claim and the
ownership contract are blockers. The tape may be worthwhile, but its current
word bound and single-pass exact-allocation story are not a specification.

The recommended first slice is:

1. Define owned and borrowed lifetimes, checked versus trusted guarantees,
   and complete-buffer scope. Keep safe owned bytes private; expose explicit
   borrowed zero-copy access only under its lifetime contract.
2. Add kin head/span/structural-skip and checked navigation primitives over
   already fully validated bytes. In the initial shipped path, a view opens
   through the full scanner, then the VM when available; support linear map
   lookup and an O(depth) sequential cursor, with exact scalar accessors,
   copied materialisation and explicit raw-span behavior.
3. Measure open-plus-one-field and sequential/repeated access against full
   decode/cbor.mjs, including memory and ownership costs. Prototype one
   bounded per-container child directory behind a private option if repeated
   access justifies it; specify its complete addressing before freezing it.
4. Defer implicit lazy positional validation, a universal dense tape, and
   replacing encode with an end-sorting writer until their proof contracts
   and cost gates are resolved. Preserve the current encoder as the measured
   baseline. An explicit detached-subtree validation operation is a simpler
   later addition than pretending a key lookup determines its enclosing
   schema obligations.

That slice delivers “check once, materialise only what is used” while
preserving profile §5, the frozen VM semantics, and the option to add faster
navigation from measured evidence.
